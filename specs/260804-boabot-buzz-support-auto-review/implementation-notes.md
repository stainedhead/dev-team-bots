## WS-A (FR-001, FR-007) — 2026-08-04

**Auth-tag secret format — confirmed, not assumed.** `data-dictionary.md`/`research.md`'s proposed `owner_pubkey_hex|conditions|sig_hex` format was verified directly against `nipoa.go`'s actual signatures before committing to it in code: `SignAuthTag` returns `[]string{"auth", ownerPK.Hex(), conditions, hex.EncodeToString(sig.Serialize())}`, and `ValidateAuthTag` destructures `tag[1], tag[2], tag[3]` as `ownerHex, conditions, sigHex` — the pipe-delimited fields map onto `tag[1:4]` exactly, in order. Delimiter safety also confirmed: `ValidateConditions` rejects whitespace and every valid clause is anchored to `kind=<decimal>` / `created_at<<decimal>` / `created_at><decimal>` joined by `&`, so a literal `|` can never appear inside a valid `conditions` string, and the other two fields are hex — pipe-delimiting cannot silently misparse a legitimate value.

**Deviation from the task brief's test-harness instruction.** WS-A1's brief said to write the Red test using "the existing Phase D test harness's recording `dialFunc`/`fakeConn` seam" from `cmd/boabot/main_test.go`. This is not reachable: `dialFunc` (`conn.go`) returns the unexported interface `relayConn`, so no function literal satisfying `WithDial`'s parameter type can be written outside `package buzz` — `cmd/boabot` is `package main`. Rather than build a real NIP-01/NIP-42-speaking test WebSocket server (out of proportion for a wiring fix), the Red/Green tests instead assert the two things FR-001 is actually about, at the layer that's genuinely testable with exported API only: (1) `buildBuzzMonitor` now requests `buzz_auth_tag` through the `SecretStore` (the concrete evidence the wiring gap existed and is now closed), and (2) `buzzinfra.LoadAuthTag`'s returned `AuthTagFunc` produces a tag that is byte-identical to `SignAuthTag`'s own output and independently passes `ValidateAuthTag` — the same tag `internal/infrastructure/buzz/phase_e_wiring_test.go`'s `TestE3_NIPOAAuthTagIncludedOnAuthEvent` (unmodified by this workstream) already proves ends up on the signed AUTH event once `WithAuthTagFunc` carries it. That existing test, and its negative control `TestE3_NoAuthTagFuncOmitsAuthTag`, were re-run and both still pass unmodified — confirming the AUTH-event half of the mechanism this workstream wires into was already correct and needed no change.

**Red (WS-A1):** `cmd/boabot/main_test.go`'s `TestBuildBuzzMonitor_AuthTagSecretIsResolved` — configures a resolvable, well-formed `buzz_auth_tag` secret (a real owner-signed tag via `buzzinfra.SignAuthTag`, joined with `|`) and asserts `buzzFakeStore.calls` includes `{Name: "buzz_auth_tag", Bot: "buzzbot"}`. Confirmed compiling and failing against `HEAD` (`buildBuzzMonitor`'s `opts` only ever appended `WithLogger`/`WithProfile`/conditionally `WithAPIToken`; nothing requested `buzz_auth_tag`). `TestBuildBuzzMonitor_NoAuthTagSecret_StillActivates` (negative control at the `buildBuzzMonitor` level) passed even before the Green step, since activation was already unaffected by an absent tag.

**Green (WS-A2):** Added `AuthTagSecretName = "buzz_auth_tag"` and `LoadAuthTag(ctx, store, botName, agentPubkeyHex) (AuthTagFunc, bool, error)` to `internal/infrastructure/buzz/token.go`, mirroring `LoadAPIToken`'s exact shape: `errors.As` against `*secret.NotFoundError` for a clean miss (`found=false, err=nil`), `strings.TrimSpace` + empty-is-a-miss, then `strings.Split` (not `SplitN` — a stray `|` inside the signature field is a hard parse error, not silently absorbed) into exactly 3 fields, building the 4-element `["auth", ...]` tag and validating it via the existing `StaticAuthTagFunc` before returning. In `cmd/boabot/main.go`'s `buildBuzzMonitor`, added a block mirroring the `LoadAPIToken` block immediately above it: on error, `slog.Warn` and continue (not fail-closed); on a resolvable, valid tag, `opts = append(opts, buzzinfra.WithAuthTagFunc(authTagFn))`. Also fixed the `BuzzConfig` doc-comment overclaim FR-001 called out as "worse than a simple omission": the comment named `PrivateKeySecretName`/`APITokenSecretName` as the resolution path for an auth tag that didn't exist yet — now also names `AuthTagSecretName`, which does.

Additional Green-step tests added directly against `LoadAuthTag` (exported, callable from `cmd/boabot`): well-formed resolve+validate round-trip, clean miss, malformed field count (2 and 5 fields), tampered/non-verifying signature, and empty-but-legal `conditions` (`owner||sig`). Plus `TestBuildBuzzMonitor_InvalidAuthTagSecret_LogsAndContinues` proving the log-and-continue path at the `buildBuzzMonitor` level.

**Refactor (WS-A3):** Documented `buzz_auth_tag`'s pipe-delimited format, provisioning commands, and the "opaque string, boabot parses it, no `--format` flag" decision (OQ-R1) in `user-docs/Buzz-Adoption-Config.md`, alongside the existing `buzz_private_key`/`buzz_api_token` table — new "Optional: the NIP-OA owner-attestation tag (`buzz_auth_tag`)" subsection under Step 3.

## WS-D (FR-005) — 2026-08-04

**Red:** Added `TestMonitor_Dispatch_OversizedContent_RejectedNotDispatched` (`internal/infrastructure/buzz/monitor_test.go`): a `kind:9` mention event with a 2 MiB `Content` (`strings.Repeat("a", 2*1024*1024)`), asserting `MessageQueue.Send` is never called and the rejection appears in structured logs naming the event ID and content size. Confirmed failing against `HEAD` (`dispatch` had no size check, so the oversized content was dispatched).

**Green:** Added `maxContentLen = 64 * 1024` (64 KiB) as a package constant in `monitor.go`, checked in `dispatch` immediately after the empty-content check and before the author gate (an oversized attempt is worth logging regardless of sender; no reason to spend a gate check on content that will be rejected anyway). On rejection, logs `slog.Warn` with `event_id`, `content_len`, `max_content_len`, and `channel`, then returns without building a `TaskPayload`.

**Bound chosen — 64 KiB — and reasoning:** Generous for any legitimate multi-paragraph chat-style message (Nostr relays/clients commonly cap event/content sizes in a similar tens-of-KB range), while closing off the uncontrolled-token/cost-spend concern FR-005 raised. Not a demonstrated live exploit per the PRD's own framing — this is defense-in-depth, so the bound favors generosity over tightness.

**Refactor / AD-4 (constant vs. `Monitor.Config` field):** Kept as a package constant, matching AD-4's default and OQ-R2/FR-007's precedent (don't add operator-tunable surface without a demonstrated need). No concrete reason surfaced during implementation to promote it — no existing test fixture needed a non-default bound, and no operator-facing requirement calls for tuning it. Documented directly on the constant's doc comment in `monitor.go`, including the promotion path (`Config.MaxContentLen`, defaulting to the constant when zero, mirroring `PresenceInterval`) if a real need shows up later. No `docs/architectural-decision-record.md` edit here — left for WS-B5's collection pass per `architecture.md` AD-2.

**`discovery.go` — deliberately untouched.** The PRD's acceptance criteria targets a `kind:9` event exceeding the bound being rejected "before becoming a `TaskPayload`" — `discovery.go`'s `kind:39000` metadata handling (`logChannelMetadata`) never builds a `TaskPayload`; it only logs a screened `name`/`about` pair. `kind:39000` is also NIP-29 **relay-signed** metadata (per `monitor.go`'s own kind-constant comments), a narrower attacker-control surface than `kind:9`, which any channel member can publish. The Green guidance's "and/or `discovery.go`'s metadata handling" and "if practical, a max-tag-count check" are both optional ("if practical"); skipped here as out of the acceptance criteria's literal scope and lower-risk. Every tag-indexing site (`trigger.go`, `discovery.go`, `nipoa.go`) was independently confirmed length-safe by the review itself (see PRD's "What Was Checked and Found Clean" section), so no tag-count bound gap was left open by this decision.
