## WS-C (FR-004) — 2026-08-04

**Test-hang bug found and fixed while resuming this workstream.** WS-C1's red test (`lock_race_test.go`) had already been written (two goroutines racing `AcquireLock` against the same path, the first stalled between file-create and content-write via an injected `acquireLockAfterCreateHook`), but running it directly (`go test -run TestAcquireLock -v ./internal/infrastructure/buzz/...`) hung past 120s instead of failing fast. Running it with `go test -timeout 15s -run TestAcquireLock -v ./internal/infrastructure/buzz/...` produced a goroutine dump that pinpointed the cause precisely: the test used `sync.Once` (`stallOnce.Do(...)`) to ensure only the *first* goroutine to reach the hook stalls. But `sync.Once.Do` does not let a second, concurrent caller skip through while the first call's function is still running — it blocks the second caller on the `Once`'s internal mutex until the first call's function *returns*. In this test, goroutine A's `AcquireLock` call reaches the hook, stalls inside `stallOnce.Do`'s function body on `<-proceed`, and holds the `Once`'s mutex for the whole time. The main test goroutine's own `AcquireLock` call (goroutine B) reclaims what looks like a stale, empty lock file left by A, removes it, and retries — its retry's create also reaches the same hook and blocks trying to acquire the same mutex, since A's `Once.Do` call hasn't returned yet. But `proceed` (the channel that would release A) is only closed by the test *after* B's `AcquireLock` call returns — a circular wait, so the test deadlocked indefinitely rather than failing red as a TDD test must. Fixed by replacing `sync.Once` with `atomic.Bool.CompareAndSwap`: the first caller to win the CAS stalls; any later caller's CAS simply fails and it returns immediately, with no mutex to contend for. After the fix, the test fails promptly and deterministically (`both racing AcquireLock calls ... succeeded`) against the pre-FR-004 implementation, confirming it is a genuine red test, and passes deterministically (`-race -count=20`) against the FR-004 fix below.

**Atomic-publish primitive chosen: `os.Link` — and, per a self-review catch, this paragraph itself originally overclaimed the verification the same way the retracted AD-3 claim did, so the precise evidentiary basis is spelled out below rather than asserted as settled fact.** `AcquireLock`'s write path (`lock.go`) now goes through `publishLockFile`: the PID is written to a same-directory temporary file (`os.CreateTemp`), `fsync`'d, and closed — this file is never visible under the lock's final path — and only then published under the lock's final name via `os.Link(tmpPath, path)`.

`os.Link` was chosen over the task brief's `O_CREATE|O_EXCL` + `os.Rename` fallback for a stronger reason than Windows-atomicity confidence alone: `os.Rename`'s own doc comment states "If newpath already exists and is not a directory, Rename replaces it" — on every platform. Two racing publishers would both `Rename` onto `path` and both succeed, providing **no mutual exclusion at all**, which is worse than the TOCTOU bug FR-004 fixes. `os.Rename` is therefore not a viable fallback for this specific requirement (atomic create-with-content-or-fail-if-target-exists); `os.Link` is the only stdlib primitive with that semantic, so there was no live alternative to weigh it against.

What was actually verified about `os.Link` on `windows` GOOS, split into what's independently confirmed versus inferred (the earlier draft of this note collapsed that distinction, which is exactly the FR-001 defect class):
- Confirmed by reading this toolchain's stdlib source directly: `os/file_windows.go`'s `Link` calls `syscall.CreateHardLink`, wrapping any error in `*os.LinkError`; `os.LinkError.Unwrap()` (`os/file.go`) returns the underlying error for `errors.Is` traversal; `syscall/syscall_windows.go`'s `Errno.Is()` maps both `ERROR_ALREADY_EXISTS` (183) and `ERROR_FILE_EXISTS` (80) to `oserror.ErrExist`.
- **Not independently verified here:** that `CreateHardLinkW` actually sets one of those two codes when the destination already exists — no Win32 documentation was read and no live Windows run was performed as part of this workstream.
- Real (if indirect) evidence that it does: Go's own `$GOROOT/src/os/os_test.go` `TestHardLink` links onto an already-existing name and asserts `IsExist(err.Err)` — with no Windows build-tag skip (only `testenv.MustHaveLink(t)`, a generic hard-link-support gate). This test runs on Go's own Windows CI builders as part of every stdlib release, which is the closest confirmation available without a local Windows machine.
- A `GOOS=windows GOARCH=amd64 go build` and `go vet` of `internal/infrastructure/buzz/...` both succeeded, confirming the code path at least compiles for that target; `GOOS=darwin GOARCH=arm64` likewise.
- Residual risk is bounded, not a safety hole: `Monitor.Start` (`monitor.go`) treats *any* non-nil `AcquireLock` error identically — log, decline to attach the Buzz monitor, leave everything else running (see `Monitor.Start`'s `default:` case). If `CreateHardLinkW` ever returned some other errno on Windows, `publishLockFile` would surface it as a hard, non-`ErrAlreadyRunning` error rather than silently granting a second lock — a mis-typed error message, never a double-granted lock.

`GOOS=windows GOARCH=amd64 go build ./internal/infrastructure/buzz/...` and `GOOS=darwin GOARCH=arm64 go build ./internal/infrastructure/buzz/...` both confirmed the package still cross-compiles cleanly. AD-3 (`architecture.md`) is resolved by this evidence, though the file edit itself is left for WS-B5's collection pass per AD-2, matching WS-D/WS-A's precedent of not touching `docs/architectural-decision-record.md`/`docs/technical-details.md` directly.

**Refactor (WS-C3):** `readLockPID`'s doc comment updated to state precisely which crash window FR-004's fix closes: an empty file under the lock's final path can no longer be produced by `AcquireLock`'s own current write path (publication is now atomic — there is no create-then-populate step observable under the final name), so the empty-file branch now exists only for lock files predating this fix (e.g. a zero-byte file left by an older binary's `O_CREATE|O_EXCL`-then-`WriteString` sequence crashing mid-write) or other genuinely-empty on-disk artifacts, not a currently-reachable in-process race.

## WS-B (FR-002 + FR-003, combined) — 2026-08-05

**Process note, for anyone reading this later:** this workstream took three attempts. The first agent stalled 600s without writing any code (mid-deliberation on test design, working tree untouched). A resumed attempt — briefed with a concrete, line-numbered analysis of the actual bug in `attachSub`/`Subscribe`/`removeAndClose`/`Close` rather than the review PRD's more abstract description — stalled again in the same way. At that point the orchestrator implemented the fix directly rather than risking a third stall, using the same concrete analysis. Recorded here in case the pattern (long, open-ended deliberation before ever writing a failing test) recurs on other subtle-concurrency findings in future review cycles — the fix that worked was handing over a precise bug analysis (exact line numbers, exact interleaving, exact current-code behavior) up front, not asking the agent to derive it from the review PRD's abstraction.

**The bug, precisely.** `Subscribe` registered a new `subEntry` into `rc.subs` under `subMu`, released `subMu`, and only then called its own `attachSub`. In that window, a concurrent reconnect's `resubscribeAll` (running after every successful reconnect) could observe the same, not-yet-attached entry and call `attachSub` on it too — `attachSub`'s only guard was "is this entry still registered," not "is this entry already attached." Both calls would succeed, both would call `conn.Subscribe` (two independent underlying library subscriptions for one logical entry), and both would overwrite `entry.pumpDone` — a single-slot channel — so the *earlier* attach's completion signal became unreachable. `removeAndClose` waited only on `entry.pumpDone` (whichever attach wrote it last) before calling `close(entry.out)`; the orphaned earlier generation's pump, still running, had no one waiting on it and could still be forwarding — its next send on the now-closed `entry.out` would panic (`send on closed channel`), an unrecovered panic that crashes the whole `boabot` process, not just the Buzz monitor. `Close()` itself was already safe against the full-shutdown case (it waits on the *global* `rc.pumpWG`, which every pump — orphaned or not — decrements), but `removeAndClose`'s single-subscription teardown path had no equivalent.

**The fix.** `subEntry` gained a `generation int` (subMu-guarded) and a per-entry `sync.WaitGroup` (`wg`), replacing `pumpDone`. `attachSub` no longer tries to *prevent* a concurrent double attach — distinguishing "a legitimate re-attach after a real reconnect" from "a duplicate attach of a never-yet-attached entry" isn't knowable locally, and a false rejection would silently drop a subscription. Instead it makes a double attach *safe*: every successful attach bumps `entry.generation` and calls `entry.wg.Add(1)` before starting its pump; `pumpSub` compares its own captured generation against the live `entry.generation` before every forward and exits silently the moment it's superseded, so at most one generation's pump is ever actively delivering; `removeAndClose` waits on `entry.wg` — every generation ever started, not just the latest — before closing `entry.out`, so an orphaned pump can never still be sending when the channel closes.

**FR-003's mechanism.** The entry-existence check, the generation bump, and the `entry.wg`/`rc.pumpWG` `Add()` calls all happen inside one `rc.mu`-guarded critical section in `attachSub` — the *same* lock `Close()` uses to set `rc.closed = true`. Since mutex critical sections are totally ordered, this makes the two operations strictly sequenced from any interleaving: either `Close()`'s `closed = true` transition completes first (a subsequent `attachSub` call sees it and refuses before ever calling `Add()`), or `attachSub`'s `Add()` completes first while `rc.mu` is held (which, via the mutex's own memory-ordering guarantees, makes that `Add()` visible-before `Close()` can acquire `rc.mu` itself, and therefore before its later `rc.pumpWG.Wait()` — so `Wait()` correctly counts and waits for it rather than the `Add()`/`Wait()` race that Go's own `sync.WaitGroup` documentation warns produces undefined behavior). This is a deliberate departure from the review PRD's suggested `atomic.Bool` for `rc.closed` — a mutex-based ordering achieves the same guarantee without introducing a second synchronization primitive, given the check-and-add already needed to be atomic together regardless.

**Lock-ordering audit (WS-B4).** Every `rc.mu`/`rc.subMu` acquisition in `relay_client.go` and `reconnect.go` was read directly (not inferred from an absence of an observed deadlock). Only one place ever holds both simultaneously: `attachSub`'s post-`conn.Subscribe` check, always `rc.mu` acquired first, `subMu` nested inside, released in reverse order. Every other site touches at most one lock at a time, or acquires them strictly sequentially (never nested) — `Close()` is the clearest example: `rc.mu.Lock()...rc.mu.Unlock()`, then later, separately, `rc.subMu.Lock()...rc.subMu.Unlock()`. No site acquires `subMu` and then tries to acquire `rc.mu` while still holding it, so there is no AB-BA deadlock risk.

**Tests.** `TestAttachSub_ConcurrentDoubleAttach_OnlyOneGenerationDelivers` drives two concurrent `attachSub` calls directly against the same `subEntry` — deliberately not orchestrated through the full `Subscribe`/reconnect timing (a `subscribeAfterRegisterHook` package var exists for that but isn't needed here), since a direct concurrent double-attach is the sharpest, most deterministic way to prove the fix: no sleep-and-hope timing, no flake risk. It confirms exactly one delivery reaches `entry.out` even though both attaches' underlying subscriptions receive the event, and that `removeAndClose` returns (no panic, no hang) after both generations' pumps have genuinely finished. `TestReconnect_RacingClose_NoPanicNoLeak` exercises the full path: a `reconnectAfterConnSwapHook` pauses `reconnect()` immediately after it publishes the new connection and releases `rc.mu`, right before `resubscribeAll` would run; a concurrent `Close()` is raced against it. Passed cleanly, meaning FR-003's specific interleaving was likely already close to safe before this fix (via `Close()`'s pre-existing global `pumpWG.Wait()`), but the rc.mu-guarded `Add()` in the fix removes the remaining theoretical gap rather than relying on that being sufficient by inspection alone.

**A genuine data race in the *test* itself, found and fixed.** `TestReconnect_RacingClose_NoPanicNoLeak`'s first draft reset the package-level `reconnectAfterConnSwapHook` via `t.Cleanup` immediately after the test's main assertions. `go test -race` correctly flagged this: the hook variable is *read* inside `reconnect()` (to check `!= nil` and to call it) strictly *before* the closure blocks on `<-proceed`, but nothing in the test established a happens-before edge from that read to `t.Cleanup`'s later write — the eventual `close(proceed)`/`<-proceed` synchronization only orders events *after* the block point, not the read that happened before entering the closure. Per the Go memory model this is a genuine, reportable race regardless of the fact that the read completed first on every actual run observed. Fixed by having the hook closure itself close a `hookDone` channel immediately after resuming from `<-proceed`, and having the test wait on `hookDone` before returning (and therefore before `t.Cleanup` can fire) — this establishes a real happens-before chain from the variable read, through the closure's program order, through the channel signal, to the test's continuation.

**Rigorous red-then-green verification, not assumed.** Rather than trust the analysis alone, the pre-fix `HEAD` versions of `relay_client.go` and `reconnect.go` were swapped in directly via `git show HEAD:<path>` (no `git stash`, to avoid the shared stash stack other sessions may be using), and `TestAttachSub_ConcurrentDoubleAttach_OnlyOneGenerationDelivers` was run against them: it failed 3/3 times with the exact predicted symptom — "stale generation also delivered ... got a second" — confirming the bug is real and the test genuinely exercises it, not a tautology. The fix was then restored from a backup copy and the same test passed 20/20 clean `-race` runs.

**Verification:** `go build ./...`, `go vet ./...`, `golangci-lint run` (0 issues), `go test -race -gcflags=all=-d=checkptr=0 -count=20 ./internal/infrastructure/buzz/...` (clean, both new tests), and the full repo-wide `go test -race -gcflags=all=-d=checkptr=0 ./...` (every pre-existing test across every package, unmodified and passing) all pass.
