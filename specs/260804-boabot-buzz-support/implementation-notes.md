## Technical Decisions

Decisions made during PRD/spec pre-flight, recorded here so implementation doesn't re-litigate them:

- **Scope:** full PRD, both workstreams (Buzz + Secret Storage), implemented in one dev-flow run — user's explicit choice over "Buzz P0 only."
- **OQ-1 (multi-instance singleton):** resolved as a process-level lock on the nsec (PRD option (a)), not a startup presence probe (b) or reply dedup (c). FR-031 is implemented and tested, not deferred.
- **Untestable acceptance criteria:** implemented as `//go:build integration` tests, not run automatically in this job. Flagged in this file (see below) for manual verification against real infrastructure.
- **OQ-9 (secret namespace key):** bot **name**, not bot type — consistent with `BotName` usage elsewhere in the codebase.
- **Other non-blocking open questions (OQ-2, OQ-3, OQ-4, OQ-5, OQ-6, OQ-8, OQ-10, OQ-11):** not resolved with a hard decision — implementation proceeds per the PRD's own stated lean where a concrete choice is unavoidable (e.g., OQ-2 doesn't block implementing FR-005–007 since attestation *validation* doesn't require deciding the *issuance* workflow); genuinely deferred items (OQ-5 `boabotctl` attestation tooling, OQ-6 NIP-AE engrams) remain out of this implementation's scope per the PRD's own P1/P2 phasing.
- **OQ-11 resolved for `boabotctl secret` (FR-049):** local machine only, no remote-bot writes. Simpler and matches the PRD's stated lean.

## Decisions made during spec review (Step 2)

Recorded here so Step 3 implementation doesn't have to re-derive them from the review conversation:

- **Scope resolution (spec.md/plan.md/tasks.md were inconsistent before this review):** the full in-scope FR range for this run is FR-001–FR-054, including FR-025 (typing), FR-026 (gated `!shutdown`), and FR-027 (reactions) pulled forward from PRD P1 — `plan.md`'s Phase F already implemented them, and leaving them out while implementing everything else in Phase F would have left in-progress code contradicting the phasing doc. FR-048 is in scope for its warn-only clause only; the post-deprecation hard-rejection trigger is deferred one release, per the PRD's own P2 phasing. See `spec.md` §Timeline and Milestones and `tasks.md` §Deferred Items for the authoritative list.
- **`domain.Event`/`domain.Filter` are domain-owned types, not `fiatjaf.com/nostr`'s library types.** `data-dictionary.md` previously left this "TBD, likely reused directly" — that would fail the PRD's own `grep -r "fiatjaf.com/nostr" internal/domain` acceptance criterion. `internal/infrastructure/buzz/relay_client.go` now owns a translation layer between the two, itself a tested component (`tasks.md` D3).
- **`boabotctl`'s secret subcommands (FR-049) cannot share code with `boabot`'s `internal/infrastructure/secret/keystore`** — different Go module, and `internal/` visibility is per-module-root. `boabotctl` takes its own `zalando/go-keyring` dependency and only shares the FR-045 key-naming *convention* with `boabot`, not code. See `architecture.md` §Cross-Module Constraint.
- **Edge cases with no prior design note, now resolved** (see `architecture.md` §Edge Cases and Failure Paths for full detail): FR-022 reply-publish failure (log, don't re-enqueue — the worker already ran); per-secret-provider timeout (2s per provider via `context.WithTimeout`, a timeout is a miss not an error); the pending task-ID map is untouched across reconnect (only connection/auth/subscriptions are re-established); the presence ticker suspends while disconnected and resumes on reconnect; `respond_to_allowlist` nil (no gate) vs. explicit empty list (allow-none) are distinct configurations.

## Phase B — Secret storage domain + providers (complete)

**B1 spike findings** (resolves `research.md`'s two `[needs implementation research]` items scoped to this phase):

- **`zalando/go-keyring` (confirmed at `v0.2.8`, the actual latest via `go get github.com/zalando/go-keyring@latest` — matches the PRD's own research):**
  - `keyring.Get(service, user string) (string, error)`, `keyring.Set(service, user, password string) error`, `keyring.Delete(service, user string) error`, `keyring.DeleteAll(service string) error`; `keyring.ErrNotFound` and `keyring.ErrSetDataTooBig` sentinel errors. Confirmed by reading `keyring.go` in the module cache.
  - **Darwin write path verified stdin-only, never argv:** `keyring_darwin.go`'s `Set` runs `exec.Command("/usr/bin/security", "-i")`, opens a `StdinPipe`, and writes the full `add-generic-password ...` command (with the password base64-encoded and shell-escaped) to that pipe — the password is never a `Cmd.Args` element. `Get`/`Delete` use `-s`/`-a` flags with the service/user only (never the secret). This directly satisfies FR-052 for the one backend that shells out at all; Linux (D-Bus via `godbus/dbus`) and Windows (`danieljoos/wincred` syscalls) never invoke a subprocess.
  - The library ships its own test seam, `keyring.MockInit()` / `keyring.MockInitWithError(err)`, which swaps the package-level backend for an in-memory map — used throughout `internal/infrastructure/secret/keystore`'s tests so no test ever touches a real OS keystore or spawns `/usr/bin/security`.
  - Since our own `keystore.Provider` never constructs an `exec.Command` itself (it only calls the library's package-level functions), FR-052's "no subprocess argument" AC is satisfied by (a) the library-source verification above and (b) a mechanical regression test, `TestProvider_SourceNeverConstructsASubprocessDirectly`, that scans the package's own non-test `.go` source for `os/exec`/`exec.Command` and fails if either appears — guarding against a future edit reintroducing a direct subprocess call here.
- **systemd `$CREDENTIALS_DIRECTORY` semantics (confirmed via `https://systemd.io/CREDENTIALS/`):** one regular file per credential, named after the credential ID, under the directory named by `$CREDENTIALS_DIRECTORY`; access restricted to the service's user, enforced by the kernel. The documentation does **not** specify a trailing-newline convention for file content. **Decision:** the systemd provider defensively strips a single trailing `\n` (credentials are often authored by hand or via `echo`/`printf` into `SetCredentialEncrypted=` inputs) and treats an unset `$CREDENTIALS_DIRECTORY` and a missing/empty-after-trim file as ordinary misses (not errors) — a genuine read error (e.g. the credential path unexpectedly being a directory) is still surfaced as an error, not swallowed. Live verification of exact byte-for-byte behavior against a real systemd unit remains on the manual-verification checklist below (`tasks.md` I2).

**Design decisions (B2–B10), recorded so later phases don't re-derive them:**

- `internal/domain/secret.go` contains exactly `SecretRef`, `SecretProvider`, `SecretStore` (per the task's explicit enumeration) — zero infrastructure imports, only `context`. The concrete ordered-chain implementation (`Store`, implementing `domain.SecretStore`) and its `NotFoundError` type live in `internal/infrastructure/secret/store.go` instead, since FR-038 only requires the *interfaces* to live in domain and the chain-composition logic, while dependency-free itself, is orchestration that belongs with the providers it composes.
- **Per-provider timeout is enforced at the `Store` call boundary via a goroutine + `select`, not by relying on providers to observe `ctx`.** All four real providers are synchronous local calls (env var read, file read, `os.ReadFile`, or a `zalando/go-keyring` call) that do not thread `ctx` into anything cancellable. Wrapping each `Lookup` call in its own goroutine with a `context.WithTimeout` select means a genuinely hung provider (e.g. an unresponsive D-Bus round trip) cannot block the chain past the timeout, at the cost of a leaked goroutine in that specific failure case — an accepted, documented tradeoff (`store.go`'s `callProvider` doc comment).
- **Key/namespacing convention (FR-045, threaded through B4–B7 per B8):** bot **name** (not type, per OQ-9). `env`: ignores `Bot` entirely (FR-044 — env vars are process-global; the var name is `strings.ToUpper(ref.Name)`). `file`/`systemd`/`keystore` are all **strict-match, no fallback**: when `Bot` is set, only the bot-scoped key (`"<bot>_<name>"` for file/systemd; service `"boabot"` + account `"<bot>/<name>"` for keystore) is consulted; when `Bot` is empty, only the bare `"<name>"` key is consulted. **Deliberately no fallback from a bot-scoped lookup to the global key** — an earlier draft had the file provider fall back to the global key when the bot-scoped one was absent, which would let a per-bot secret (e.g. a Buzz nsec) silently resolve to a differently-scoped global entry, meaning two bots could end up unknowingly sharing one private key. Caught during self-review (advisor pass) before commit; fixed to match systemd/keystore's already-strict behavior, with a regression test (`TestProvider_Lookup_BotSet_DoesNotFallBackToGlobal`) added. These conventions are documented in each package's doc comment and are the stable on-disk/on-keychain contract per FR-045.
- **FR-052 verification is two-layered, not source-grep alone.** An earlier draft's only FR-052 test scanned the keystore package's own source for `exec.Command`, which proves this package never shells out but says nothing about the argv zalando/go-keyring itself constructs — a future library upgrade that regressed darwin's `Set` to pass the password via `-w <password>` on argv would have left that test green. Fixed by adding `TestProvider_Set_ConstructsCallWithSecretOnlyInPasswordSlot`, which injects a recording fake `backend` and asserts the secret only ever lands in the library's dedicated `password` parameter of `Set(service, user, password)`, never spliced into `service` or `user` (the two arguments that *do* appear as `-s`/`-a` argv flags on darwin). Combined with the B1 spike's direct reading of `keyring_darwin.go` (documented above), this covers both the boundary we control (our own call construction) and the boundary we don't (the library's own transport, which is out of scope to re-verify per-run but is now unit-tested with a stronger regression signal at our seam). The source-grep test (`TestProvider_SourceNeverConstructsASubprocessDirectly`) is kept as a cheap complement.
- **`keyring.MockInit()`/`MockInitWithError()` are process-global state** (they set a package-level variable inside `zalando/go-keyring`). Every test that calls `MockInitWithError` does so via a small `mockInitWithError(t, err)` helper (in both `keystore/provider_test.go` and `no_value_logging_test.go`) that registers `t.Cleanup(keyring.MockInit)`, so a failing backend never leaks into whatever test runs next in the same binary — removing an ordering dependency between tests in these files.
- **FR-043's "world-readable file remains fatal" is satisfied at the provider level, not specially by `Store`:** `file.Provider.Lookup` returns `credentials.Load`'s error unchanged (verified by test to preserve the exact message and remediation hint) rather than downgrading it to a miss. `Store.Get`'s generic FR-039 behavior (any provider error is non-halting, chain continues) still applies uniformly — no special-casing for the file provider inside `Store`. The full system-level guarantee that a world-readable file refuses process startup is delivered by Phase C's `main.go` wiring (C1, out of scope for Phase B), which can recover the original message via `errors.As` against `Store`'s `NotFoundError.Unwrap() []error`.
- **`NotFoundError`** (FR-053) names the reference (`Name`, `Bot`) and enumerates every provider consulted in order; it also implements `Unwrap() []error` so callers can `errors.Is`/`errors.As` into the specific underlying provider errors it collected, without those errors' text needing to appear verbatim in `NotFoundError.Error()`'s own message (though it does include them for operator-facing diagnostics too).
- **FR-051 (provider half):** none of the four providers call any logger themselves; only `Store` logs (`provider=<name> timeout` / `provider=<name> error`), and only ever with the provider name and reference name, never a value. Verified by `internal/infrastructure/secret/no_value_logging_test.go`, a cross-provider test driving all four real providers' error paths (plus a hit path) through a captured `slog` buffer with a sentinel secret value, asserting the sentinel never appears in log output or in any returned error string — complementing each provider package's own narrower version of the same assertion.
- **Coverage:** 100% of statements on `internal/domain` (the new `secret.go` — trivial, interfaces only) and on all of `internal/infrastructure/secret/{,env,file,keystore,systemd}`.

## Phase C — Secret storage callers (complete)

**Design decisions (C1–C5), recorded so later phases don't re-derive them:**

- **C1 (`cmd/boabot/main.go`):** the two former `applyCredential` calls are replaced by `resolveEnvCredentials`, which calls a new `applyCredentialFromStore(ctx, store, secretName, envKey)` helper against a `secret.Store` built by `buildSecretProviders()` (env → systemd → keystore → file, matching FR-040's default order). Precedence ("an explicit env var always wins") is **not** re-implemented in `main.go` — it falls out of `Store`'s own provider ordering, since `env` is always tried first and returns on a hit. `applyCredentialFromStore` is therefore a thin `Get`-then-`Setenv` wrapper; when the store misses, `envKey` is left exactly as it was (matching pre-migration behaviour byte-for-byte). The pre-existing "world-readable `~/.boabot/credentials` is fatal at startup" guard is preserved as a literal, unconditional `credentials.Load` call inside `buildSecretProviders()` — run *before* the file provider is ever added to the chain and independent of which individual secrets are actually needed — because delegating that guard to lazy chain resolution would only trigger it when every earlier provider (env, systemd, keystore) had already missed, silently skipping the check whenever `ANTHROPIC_API_KEY`/`BOABOT_BACKUP_TOKEN` were already supplied via env var. If `credentials.DefaultPath()` itself fails (home dir undeterminable), the file provider is omitted from the chain entirely rather than passed an unusable path — matching the old code's behaviour of skipping the whole credentials-file block in that case.
- **Accepted behaviour delta (not a regression, but worth flagging):** for a credentials-file-only deployment, secret resolution now consults `systemd` and `keystore` before `file` on every startup — a new (inert, but non-zero-cost) `$CREDENTIALS_DIRECTORY` env read and an OS keystore round trip (a `/usr/bin/security` subprocess on macOS) that never happened pre-migration, plus up to 2s×2 of stall if either is unresponsive. The chain order is not negotiable (FR-040), and the "byte-identical **config**" AC (FR-046) still holds — this is a startup-cost/robustness note, not a functional regression. Cross-referenced with the existing macOS-LaunchDaemon keystore-reachability item on the manual-verification checklist below, since that's the scenario most likely to surface a slow/unresponsive keystore call at boot.
- **C2 (`SlackConfig.ResolveSecrets`, in `internal/infrastructure/config/config.go`):** a new method on `*SlackConfig` takes `(ctx, domain.SecretStore, *slog.Logger)`. When `BotToken`/`AppToken` are already set inline, they win outright and a deprecation warning is logged naming the alternative (a `~/.boabot/credentials` entry or an OS keystore secret) — this is also C3's FR-048 warn-only clause. When an inline field is empty, it resolves via `store.Get(ctx, domain.SecretRef{Name: "slack_bot_token"|"slack_app_token", Bot: s.BotName})`; a store miss just leaves the field empty (not an error), matching today's "monitor only activates when all three of BotToken/AppToken/BotName are present" gate in `main.go`. **Guard added after self-review:** `ResolveSecrets` skips the store entirely when `BotName == ""`, since Slack can never activate without one anyway (`main.go`'s activation check requires all three) — without the guard, every non-Slack bot's startup would pay for two unnecessary keystore/systemd round trips for secrets that could never be used.
- **C3 (FR-048 warn-only clause):** no new production code — `SlackConfig.ResolveSecrets` (C2) is config loading's only caller of the inline-Slack-token path, and its deprecation-warning branch *is* the warn-only clause in full. Verified by a dedicated test (`TestSlackConfig_ResolveSecrets_InlineFieldsWin`, `internal/infrastructure/config/slack_secrets_test.go`) asserting the warning text names the alternative. The post-deprecation hard-rejection trigger remains out of scope this run (`tasks.md` §Deferred Items).
- **C4 (diagnostic surface — `cmd/boabot/diag.go`):** implemented as a `--diag-secrets` flag on the existing `boabot` binary rather than a new subcommand or separate tool, since `main.go` already parses flags with the stdlib `flag` package (no `cobra` dependency exists in this module) and the diagnostic needs the same config file and provider wiring as a normal run. `main()` loads `config.Config` once and branches on the flag before doing anything else. `diagnoseSecrets` deliberately does **not** call `provider.Lookup` directly — for each `(ref, provider)` pair it builds a throwaway single-provider `secret.Store` (`secret.New([]domain.SecretProvider{p}, secret.WithLogger(logger))`) and calls `Get`, so the diagnostic inherits `Store`'s per-provider timeout and non-halting-on-error semantics exactly, without any change to the already-merged Phase B `store.go` (out of this phase's scope). Output is one line per configured secret naming only the ref and the resolving provider (or, on a miss, every provider consulted) — the resolved value is discarded immediately inside `diagnoseSecrets` and never flows to `printSecretDiagnostics`. Verified by `TestPrintSecretDiagnostics_NeverPrintsSecretValue`, which feeds a sentinel value through a real hit and asserts the sentinel appears in neither the printed output nor a captured `slog` buffer (catches a future regression that logs the value directly from this package, not just from `Store`, which Phase B already covers separately).
- **C5 (`boabotctl secret set/get/delete`):** per `architecture.md`'s Cross-Module Constraint, `boabotctl` cannot import `boabot/internal/...`, so `boabotctl/internal/commands/secret.go` takes `zalando/go-keyring` as its own direct dependency and re-implements the account-naming convention (`secretAccount`: service `"boabot"`, account `"<bot>/<name>"` or bare `"<name>"`) rather than sharing code — only the FR-045 convention itself is shared, and it is documented in both places with an explicit "must stay in sync" comment. `set` reads the value via the existing `promptPassword` helper (masked terminal input, or a piped line on non-tty stdin — same mechanism `login` already uses), never via a command-line argument or flag, and rejects an empty value. **`get` reports presence/absence only, never the value** — this follows FR-049's own wording verbatim ("write, read-presence-of (never the value), and delete"), resolving the PRD's own suggested departure point in favour of the literal requirement rather than adding a `--reveal` escape hatch. `delete` on an absent entry is not an error, matching `boabot`'s own keystore provider. A `keystoreBackend` interface (mirroring `boabot`'s own test seam) keeps all six command tests off the real OS keystore. `user-docs/baobotctl.md` gained a `## baobotctl secret` section per this module's own "always update for any command change" rule.
- **Coverage:** all four new/changed call sites (`cmd/boabot/main.go`'s new functions, `cmd/boabot/diag.go`, `SlackConfig.ResolveSecrets`, `boabotctl/internal/commands/secret.go`) are covered by unit tests using fakes (`domain.SecretStore`, `domain.SecretProvider`, `keystoreBackend`) — no test in this phase touches a real OS keystore, `$CREDENTIALS_DIRECTORY`, or a real `~/.boabot/credentials` file outside of `t.TempDir()`. Two additional tests (`TestEndToEnd_EnvOnlyDeployment`, `TestEndToEnd_CredentialsFileOnlyDeployment` in `cmd/boabot/main_test.go`) exercise the real provider chain end to end — not a fake `domain.SecretStore` — for FR-046's named PRD AC ("existing deployment using only env vars, and one using only `~/.boabot/credentials`, both start with a byte-identical config to before this change"), since a fake would bypass exactly the two seams most likely to silently regress: `env.Provider`'s ref-name-to-env-var-name derivation and `file.Provider`'s bare-key convention matching the pre-migration `applyCredential` call's key names.
- **Latent cross-platform gap (not a defect in this run):** the `HOME`-env-override pattern used throughout Phase C's `main_test.go` (and inherited from Phase B) drives `credentials.DefaultPath()` via `os.UserHomeDir()`, which reads `%USERPROFILE%` on Windows, not `HOME`. These tests will fail on a Windows CI runner today. `tasks.md`'s I4 already scopes the actual multi-OS CI matrix out of this run's automated coverage, so this is tracked as a known gap for that later item, not fixed here.
