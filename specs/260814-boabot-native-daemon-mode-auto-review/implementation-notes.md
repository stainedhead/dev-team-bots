# Implementation Notes: Boabot Native Daemon Mode — Code Review Fixes

**Created:** 2026-08-14

Record technical decisions, edge cases, deviations from the plan, and lessons learned as implementation proceeds. Update this file continuously during Phase 5 — do not leave it until the end.

## Technical Decisions

- **FR-101 fix shape:** split `markSeenIfDuplicate` into two methods — `isDuplicateEvent` (peek-only, still does the lazy-eviction sweep since it's called on every `Dispatch`) and `markEventSeen` (side-effecting, called only from `Dispatch`'s success paths: the `chatMgr` "handled" branch and the plain-dispatch success branch, both right before their `return`). `markEventSeen` no-ops on an empty `eventID` to preserve the original "no dedup for empty event ID" behavior without needing an `if eventID != ""` guard at every call site.
- **FR-102 fix shape:** `buzzBoardTitle` now compares `utf8.RuneCountInString(title) > boardItemTitleMaxLen` and slices `[]rune(title)[:boardItemTitleMaxLen]` instead of `title[:80]`. `boardItemTitleMaxLen` (80) is now a rune count, not a byte count — matches the acceptance criterion's intent (a short *readable* title) better than a byte cap anyway.
- **FR-103:** wrote the nil-builder-for-one-persona test per the acceptance criterion (two Buzz-enabled personas, builder returns `nil` for one and a real `*mocks.ChannelMonitor` for the other). It passed immediately against the existing code — the `if mon == nil { continue }` branch was already correct, just uncovered (confirmed via the raw coverage profile: `team_manager.go:397.18,398.13` went from hit-count 0 to 1). No production code change. Added a `Monitors()` test-only accessor to `export_test.go` (mirrors the existing `ResolvedPluginStore()`/`ResolvedInstallDir()` pattern) so the test can assert exactly one monitor was registered.

## Edge Cases & Solutions

- FR-101: the regression test uses the same `fakeScheduledDispatcher` the rest of the suite already uses, mutating its `err` field to `nil` between the first (failing) and second (retried) `Dispatch` call with the identical event ID — this reproduces "transient failure, then relay redelivers" without needing a new fake.
- FR-102: verified rune-safe truncation against three cases per the acceptance criterion — a 78-ASCII-byte + 10-rune-Japanese-suffix string (mid-rune boundary under the old byte-based cap), an all-whitespace instruction (empty-fallback path), and a 100-char pure-ASCII instruction (must truncate identically to the old byte-based behavior). All three verified via `buzz.getCreated()[0].Title` since `buzzBoardTitle` itself is unexported and the test file is in `orchestrator_test` (external test package).

- **FR-101 revision (post-advisor-review):** the first FR-101 fix (peek-only `isDuplicateEvent` + a separate `markEventSeen` called after success) satisfied the acceptance criterion's sequential test but reintroduced a *logical* (non-`-race`-visible) TOCTOU: two concurrent `Dispatch` calls for the identical event ID could both pass the peek and both dispatch, double-creating a `DirectTask`/board item -- the exact double-create spec.md's "Relay reconnect / message replay" edge case forbids. Verified the production calling pattern first (`internal/infrastructure/buzz/discovery.go`'s `consumeChannel`: one goroutine per channel subscription, events handled serially in a `for { select }` loop; `subscribeToChannel` is idempotent so only one such goroutine exists per channel at a time) -- so this race cannot occur through the real `Monitor` today. Fixed it anyway per the review PRD's own second-offered fix shape ("or explicitly un-mark the event ID before returning an error"): reverted to a single atomic `checkAndMarkSeen` (check-and-set under one lock acquisition, matching the pre-fix method's atomicity) plus a new `unmarkEvent` called on both of `Dispatch`'s error paths. Added `TestBuzzTaskBridge_ConcurrentDispatch_SameEventID_ExactlyOneProceeds` (20 goroutines, identical event ID, asserts exactly 1 dispatch + 19 `Duplicate`) to `buzz_task_bridge_concurrency_test.go`, run under `-race`.
- **FR-102 DB-column check:** verified the byte-vs-rune unit change (`boardItemTitleMaxLen` is now a rune cap, so an 80-rune CJK title can be up to ~240 bytes) doesn't hit any length-constrained storage: `internal/infrastructure/db/db.go`'s `work_items.title` column is `TEXT NOT NULL` (unbounded), and the store actually wired for Buzz board items in native daemon mode, `internal/infrastructure/local/orchestrator`'s `InMemoryBoardStore`, is a JSON file with no length constraint either. No further change needed.
- **FR-107:** repo-wide grep (`grep -rn "LoadTeamConfig" .`, not just `internal/application/team/`) confirmed the review's own claim: the only callers are `team_manager.go`'s own `Run()` and `internals_test.go` (which is `package team`, not `package team_test` -- no import/test-package change needed, just the two-symbol rename). ## Lessons Learned

- The advisor review caught a real gap in the FR-101 first-pass fix: TDD's sequential regression test (dispatch fails, redispatch, assert retried) is necessary but not sufficient for a concurrency-sensitive dedup mechanism -- it doesn't exercise the concurrent-call case at all, and `go test -race` only catches *data* races (unsynchronized memory access), not *logical* races (a correctly-locked check-then-act split across two lock acquisitions). Fixing FR-101 required both the sequential regression test AND a concurrency test that exercises N goroutines racing the identical event ID.
- Re-verifying the review PRD's own cited numbers (not just its prose claims) against current HEAD caught one small drift: the review quoted `monitor.go`'s diff as "+108/-12"; the actual verified number (`git diff 904a732 --stat`) is +108/-17. Neither the review's overall finding nor its severity changes -- but citing a freshly-verified number rather than copying the review's own is exactly the "verify, don't just re-assert" discipline AGENTS.md and the review's own Implementation Guidance both call for.
