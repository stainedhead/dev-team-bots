# Implementation Notes: ACP Harness Feature Parity

**Created:** 2026-08-15

Record technical decisions, edge cases, deviations from the plan, and lessons learned as implementation proceeds. Update this file continuously during Phase 5 — do not leave it until the end.

## Technical Decisions

- **P1.1 (FR-401):** `isConversationalSource` (`internal/application/execute_task.go`) now also matches the literal string `"acp"`. There is no `domain.DirectTaskSourceACP` constant to match against (unlike `"chat"`/`"buzz"`, which have `domain.DirectTaskSource*` constants) — ACP mode never goes through `domain.DirectTask`/`DirectTaskSource` at all (single persona, no `team.yaml`, no `DirectTaskStore`); `internal/infrastructure/acp/turn.go:47` sets `Task.Source: "acp"` as a bare string literal. Matched `"acp"` as a literal string, consistent with how `turn.go` produces it.

## Edge Cases & Solutions

- **P2.1 (FR-402): the NFR-Reliability "construction failure logged" requirement is vacuous for the board store.** `orchestratorlocal.NewInMemoryBoardStore` returns no error at all — a missing/corrupt `board.json` is silently treated as an empty board by `loadFromDisk` (swallows read/unmarshal errors), and `persist()` does its own `MkdirAll`/atomic-rename with no caller-visible failure path either. tasks.md's P2.1 acceptance criterion asks for "construction failure (bad path/permissions) logged clearly" — there is no such failure mode to catch for this store, matching `team_manager.go:449`'s own treatment (`tm.sharedBoard` constructed unconditionally with no error check). The log-and-continue treatment is real and implemented for the plugin store instead, where `NewLocalPluginStore`'s `MkdirAll` genuinely can fail (verified with a regression test using a blocked install path).
- **P3.1 (FR-404): seeded plugin/board state via the same disk-persistence mechanism the stores themselves use, rather than exposing internal store references from `buildACPMCPOptions`.** Both `InMemoryBoardStore` and `LocalPluginStore` load their state from disk at construction time; end-to-end tests write the expected on-disk shape (a `[]domain.WorkItem` JSON array for the board; a real `Install`-produced plugin directory, built via `localplugin.NewLocalPluginStore(...).Install(...)`, for the plugin store) before calling `buildACPMCPOptions`, so the function under test constructs its own fresh store instance that picks up the seeded data — no need to change `buildACPMCPOptions`'s signature just to make it testable.
- **P4.1 (FR-405): `run_opencode` (not `run_claude_code`) used for the CLI end-to-end test.** `run_claude_code` post-processes its subprocess output as `stream-json` (`codeagent.ParseStreamLine`), which would require a fake binary that emits well-formed stream-json events rather than plain text. `run_opencode` passes its subprocess stdout through unmodified, making a trivial `#!/bin/sh` fake binary sufficient to prove the full real-subprocess path (`cliagent.SubprocessRunner` via `exec.Command`) actually works end-to-end.
- **Coverage measurement command deviates from AGENTS.md's literal `go test -race -coverprofile=coverage.out ./...`.** That literal command computes each package's coverage of only its own statements, and `go tool cover -func`'s trailing `total:` line over the *whole-module* `./...` run includes every package (including ones far outside domain/application), which is not the number AGENTS.md's coverage gate refers to. Used `go test -coverpkg=<domain+application packages, excluding mocks/> <same package list>` instead, matching AGENTS.md's stated scope ("packages matching `internal/domain/...` and `internal/application/...`, excluding `mocks/`") precisely. Confirmed 92.2% — unchanged from the stated baseline, since the only application-layer production-code change (P1.1's one-line `isConversationalSource` extension) was already covered by a new test.

## Deviations from Plan

- **Scope addition beyond FR-401's literal text, required to meet spec.md's own acceptance criterion #1.** FR-401 as written only names `execute_task.go`'s `isConversationalSource`. But `cmd/boabot/acp.go`'s `buildACPAgent` never called `worker.WithChatProvider(...)` at all prior to this change (confirmed by inspection — `NewExecuteTaskUseCase(...)` was called with only `WithRulesTracker` as an optional wire-up) — so `u.chatProvider` stayed `nil` for every ACP-mode task regardless of `isConversationalSource`'s return value, making the P1.1 fix alone a no-op in production. Acceptance criterion #1 ("An ACP-sourced task with `models.chat_provider` configured runs on that provider ... test asserts provider selection, not just config presence") cannot be met without also wiring `WithChatProvider` in `acp.go`. This is the exact failure mode `docs/architectural-decision-record.md`'s ADR-B028 decision 4 already documented for the pre-existing `"chat"` branch ("dead code for every task ever dispatched") — not repeating it here. Added chat-provider wiring to `acp.go`'s (new) `buildACPWorker` helper, mirroring `team_manager.go:1047-1056`'s exact condition (`chatName != "" && chatName != cfg.Models.Default`, `pf.Get` failure logged as a warning and non-fatal, matching NFR-Reliability).
