- [x] WS-C — FR-004: `AcquireLock`'s write path (`internal/infrastructure/buzz/lock.go`) made atomic via `publishLockFile`: PID content is written to a same-directory temp file, fsync'd, closed, then published under the lock's final name with `os.Link` (EEXIST-checked; falls through to the existing stale-lock reclaim path on conflict). `os.Link` chosen over an `os.Rename` fallback after empirically confirming — via direct Go stdlib source inspection, not general knowledge — that `syscall.Errno`'s `windows` GOOS `Is()` implementation maps `CreateHardLink`'s existing-target failure codes to `fs.ErrExist`, so `errors.Is(err, os.ErrExist)` is reliable cross-platform. Also fixed a **test-hang bug** found while resuming this workstream: WS-C1's red test (`lock_race_test.go`) originally used `sync.Once` to stall only the first goroutine reaching the injected test hook, but `sync.Once.Do` blocks a *second, concurrent* caller on its internal mutex until the first call's function returns — deadlocking the test, since the second caller's `AcquireLock` call (recreating the lock after reclaiming what looked like a stale lock) also reached the hook while the first was still stalled. Replaced with an `atomic.Bool` CAS so only the first caller stalls and any later caller returns immediately. `go build`, `go vet`, `golangci-lint run`, `go test -race -gcflags=all=-d=checkptr=0 ./internal/infrastructure/buzz/... -count=20` all pass; `GOOS=windows GOARCH=amd64` and `GOOS=darwin GOARCH=arm64` cross-compiles of the package both succeed.
- [x] WS-B — FR-002 + FR-003 (combined, one commit, shared root cause): `subEntry` gained a `generation int` (bumped by `attachSub` on every attach) and a per-entry `sync.WaitGroup` (`wg`), replacing the single-slot `pumpDone` channel. `attachSub` no longer tries to prevent a concurrent double attach (Subscribe's own initial attach racing a concurrent reconnect's `resubscribeAll` attaching the same not-yet-attached entry, or vice versa) — it makes one safe: every attach gets its own generation, `pumpSub` checks `entry.generation != myGen` before each forward and silently exits if superseded, and `removeAndClose`/`Close` wait for every generation's pump (`entry.wg.Wait()` / the existing global `rc.pumpWG.Wait()`) rather than just the latest, so an orphaned earlier-generation pump can never still be sending when the channel closes. FR-003 (reconnect vs. `Close()`): the entry-registration check, the generation bump, and `entry.wg`/`rc.pumpWG.Add()` all happen inside one `rc.mu`-guarded critical section — the same lock `Close()` uses to set `rc.closed = true` — so the two are strictly ordered: either `Close()`'s transition happens first (a later `attachSub` then sees `rc.closed` and refuses) or `attachSub`'s `Add()` happens first (and is therefore guaranteed visible to `Close()`'s later `rc.pumpWG.Wait()`). Lock ordering audited by direct reading of every `rc.mu`/`rc.subMu` acquisition site in both files (WS-B4): only one place ever holds both simultaneously (`attachSub`'s new second check), always `rc.mu` outer / `subMu` inner, never the reverse — no deadlock risk. Two new tests: `TestAttachSub_ConcurrentDoubleAttach_OnlyOneGenerationDelivers` (drives two concurrent `attachSub` calls directly — the sharpest, most deterministic way to prove the fix, no sleep-and-hope timing needed) and `TestReconnect_RacingClose_NoPanicNoLeak` (a `reconnectAfterConnSwapHook` pauses `reconnect()` right after the connection swap, racing a concurrent `Close()`; this test's own first draft had a genuine data-race in its *test* cleanup — a global test hook read in one goroutine and reset via `t.Cleanup` in another with no happens-before edge between them, per Go's memory model, even though the read completed first in wall-clock time on every observed run; fixed by adding a `hookDone` signal channel the test waits on before returning). **Rigorously verified red-then-green**: swapped in the pre-fix `HEAD` version of both source files (via `git show HEAD:...`, no stash), confirmed `TestAttachSub_ConcurrentDoubleAttach_OnlyOneGenerationDelivers` genuinely fails 3/3 runs against it (duplicate delivery, exactly the bug the review found), then restored the fix and confirmed 20/20 clean `-race` runs. `go build`, `go vet`, `golangci-lint run`, `go test -race -gcflags=all=-d=checkptr=0 -count=20 ./internal/infrastructure/buzz/...`, and the full repo-wide `-race` suite all pass.
