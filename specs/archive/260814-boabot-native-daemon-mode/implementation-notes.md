# Implementation Notes: Boabot Native Daemon Mode (Multi-Agent Buzz Support)

**Created:** 2026-08-14

Record technical decisions, edge cases, deviations from the plan, and lessons learned as implementation proceeds. Update this file continuously during Phase 5 — do not leave it until the end.

## Technical Decisions

### P1.0 — Traced current Buzz → `Worker.Execute` call site

Exact current path (no `Dispatcher`/`DirectTaskStore`/`BoardStore` involvement anywhere):

1. `internal/infrastructure/buzz/monitor.go`, `Monitor.dispatch()` (lines 385-447): on an inbound qualifying kind:9 mention, builds a `domain.TaskPayload{TaskID: uuid.New(), Instruction: ...}`, marshals it into a `domain.Message{Type: domain.MessageTypeTask, From: "buzz", To: m.cfg.BotName}`, and calls `m.queue.Send(ctx, m.cfg.BotName, msg)` directly (line 429) — this is the exact bypass: no `DirectTaskStore.Create`, no `BoardStore.Create`, nothing UI-visible.
2. That message lands on the bot's own local queue (`internal/infrastructure/local/queue`), consumed by `RunAgentUseCase.poll` → `handle` → `handleTask` (`internal/application/run_agent.go:151-182`).
3. `handleTask` (line 158-159) calls `worker.Execute(ctx, domain.Task{ID: p.TaskID, Instruction: p.Instruction, Source: string(rm.Message.From), WorkDir: p.WorkDir})` — this `worker.Execute` call (backed by `ExecuteTaskUseCase.Execute`, `internal/application/execute_task.go`) is the literal "goes straight to `Worker.Execute`" the spec describes.
4. The task's result is only ever routed back to the Buzz channel via `Monitor.HandleResult` (matched by `Monitor.pending[taskID]`, populated at dispatch time) — it is never written to any store, so it is invisible in the Tasks UI / Kanban board, exactly as spec.md states.

Contrast: the web-UI chat path (`internal/infrastructure/http/server.go handleChatSend`) calls `s.cfg.Dispatcher.Dispatch(...)` (`domain.TaskDispatcher`, backed by `internal/infrastructure/local/orchestrator/task_dispatcher.go LocalTaskDispatcher`), which creates a `DirectTask` in `DirectTaskStore` *before* sending the same shape of `domain.Message{Type: MessageTypeTask}` onto the queue via `sendMessage`. The bridge (P2.2) makes Buzz's `dispatch()` go through this same `LocalTaskDispatcher`-backed path instead of building/sending the queue message itself.

### Additional findings that reshaped the P2.2/P3.x design beyond architecture.md's sketch

1. **`domain.Task.Source` (consumed by `execute_task.go:100`) is NOT `DirectTask.Source`.** It comes from `run_agent.go handleTask`'s `Source: string(rm.Message.From)` — i.e. the *message sender identity*, not the task's origin channel. Today's `LocalTaskDispatcher.sendMessage` sets `Message.From = d.selfName` (the orchestrator persona's own bot name, e.g. `"orchestrator"`), so **the existing `task.Source == "chat"` check never actually fires for any task dispatched via `LocalTaskDispatcher`** (chat, board, or the new Buzz path) — only literal `Message.From == "chat"` would trigger it, and nothing sets that today. Confirmed via `execute_task.go`/`run_agent.go`/`task_dispatcher.go`/`http/server.go` cross-reference; the only two `domain.Task{...}` construction sites in the whole codebase are `run_agent.go:159` (queue-based, `Source` = sender bot name) and `internal/infrastructure/acp/turn.go:44` (`Source: "acp"`, untouched by this work).
   - **Decision (deviation from architecture.md's literal wording):** rather than just adding an `execute_task.go:100` `"buzz"` branch that would be unreachable in practice (same dead-code problem the existing `"chat"` branch already has), added a `Source string` field to `domain.TaskPayload` (`internal/domain/message.go`), set from `task.Source` in `LocalTaskDispatcher.sendMessage`, and preferred over `Message.From` in `run_agent.go handleTask` when non-empty (empty falls back to today's `Message.From` behaviour — fully backward compatible for every other message producer). This makes `execute_task.go:100`'s check reachable for real for both `"chat"` and `"buzz"` sourced tasks (its original intent), and is a **deliberate, spec-required side effect**: chat-dispatched tasks with a configured `models.chat_provider` now correctly get `chatProvider` for the first time — previously silently dead. Board/operator-sourced tasks are unaffected (their `Source` values never match the `"chat"`/`"buzz"` check either way).
2. **Latent `router.Register` double-registration panic, exposed (not created) by this feature.** `TeamManager.Run()`'s pre-registration loop (`team_manager.go` ~253-258) unconditionally calls `tm.router.Register(e.Name, 0)` for every enabled `team.yaml` entry — with no existence check. `main.go`'s Slack/Buzz wiring in `run()` already calls `router.Register(cfg.Slack.BotName, 0)` / `buildBuzzMonitor`'s `router.Register(bc.BotName, 0)` **before** `mgr.Run()` executes. Since a bot's own `buzz.bot_name` (or `slack.bot_name`) is conventionally identical to its own `team.yaml` entry name (confirmed: `boabot-team/bots/architect/config.yaml` has `buzz.bot_name: architect`, and `team.yaml` has an enabled `architect` entry), this was already a live double-registration `panic` in shipped code for any Buzz/Slack-enabled bot that is also an enabled team member — simply never exercised because native daemon mode + Buzz-enabled-and-team-enrolled has apparently never been run together before (today's only working Buzz path is ACP mode, a single-persona harness with no `team.yaml`/`TeamManager` involvement at all — matches spec.md's Problem Statement).
   - **Fix (required for P1.1's "a team with exactly one Buzz-enabled bot behaves identically to today" acceptance criterion to be true post-change, not a crash):** (a) added `Router.Lookup(botName) (*Queue, bool)` (non-panicking) to `internal/infrastructure/local/queue/queue.go`; (b) made `TeamManager.Run()`'s pre-registration loop idempotent (`Lookup`-before-`Register`); (c) `buildBuzzMonitor` now uses `Lookup`-before-`Register` instead of the old `queueAlreadyRegistered bool` parameter (also cleanly subsumes the pre-existing Slack+Buzz-same-bot-name dedup case the bool param existed for, and the new per-persona duplicate-`bot_name` edge case). Slack's own pre-`Run()` `router.Register` call in `main.go` is left untouched (out of scope for this feature) — same latent collision risk remains there in isolation and is noted here, not fixed, per AGENTS.md's "make the call, document, keep going."
3. **Monitor construction must happen inside `TeamManager.Run()`, not `main.go`'s `run()`, for the bridge to be wireable at all.** `Dispatcher`/`DirectTaskStore`/`BoardStore` (`tm.sharedTaskStore`/`tm.sharedBoard`) are created inside `Run()` itself, and every bot's `RunAgentUseCase` snapshots `tm.monitors` synchronously before any bot goroutine starts — so channel-monitor registration must complete, synchronously, inside `Run()` before its "start each enabled bot" loop, not from `main.go` beforehand (where the shared stores don't exist yet) and not from inside a per-bot goroutine (a data race against other bots' `tm.monitors` snapshot). **Decision:** added `TeamManager.WithBuzzMonitorBuilder(BuzzMonitorBuilder)` — a factory hook `main.go` registers before calling `mgr.Run(ctx)`; `Run()` invokes it once per Buzz-enabled `team.yaml` entry (after `tm.sharedTaskStore`/`tm.sharedBoard` exist, before any bot goroutine starts), passing in a freshly-built `LocalTaskDispatcher` + `tm.sharedBoard`. `main.go`'s closure builds a per-persona `BuzzTaskBridge`/`ChatTaskManager` pair and delegates to (now-modified) `buildBuzzMonitor`. `cmd/boabot/main.go` still owns all infrastructure construction (`buildBuzzMonitor` unchanged in spirit, `SecretStore`, relay client, etc.) — only the *invocation timing* moves into `TeamManager`, matching this file's existing precedent of importing infra packages directly (unlike `domain`/`application/*` proper, `internal/application/team` is already a per-bot composition-root helper, not a pure use-case package — it already imports `internal/infrastructure/http`, `local/queue`, `local/orchestrator`, etc. directly).
4. **Per-persona isolation via separate `BuzzTaskBridge`/`ChatTaskManager` instances, not a shared one.** Each Buzz-enabled persona's monitor gets its own `BuzzTaskBridge` (own event-ID dedup map) and its own `ChatTaskManager` (own scheduling-confirmation pending map, keyed by Buzz channel UUID as `threadID`). This is what actually satisfies FR-004's "no cross-talk" for the scheduling confirm/cancel flow: two personas mentioned in the same Buzz channel each have their own confirmation state, so a bare "yes" from a user can never confirm the wrong persona's pending intent (a plain shared-instance + `channelUUID`-only key would have this exact bug).
5. **`InMemoryBoardStore.Create` does not fire `statusChangeHook`** (verified by reading `board.go`; only `Update` does) — creating a Buzz-originated board item directly as `WorkItemStatusInProgress` is therefore safe and does **not** spuriously trigger `techLeadPool.Allocate` (that hook only fires on a `Update`-driven `Backlog → InProgress` transition). Board items for not-yet-dispatched (future/recurring) Buzz tasks are created as `WorkItemStatusBacklog` instead, to avoid implying "queued" in the dispatch-queue-specific sense (`QueueMode`/`QueueRunAt` etc. are left unset).
6. **`ChatTaskManager.DetectAndHandle` reused as-is architecturally, but its signature is extended**: it hardcoded `domain.DirectTaskSourceChat` on the confirmation-dispatch branch, which would have mislabeled every Buzz-confirmed scheduled task as chat-sourced (violating the NFR-Observability "traceable per-agent, not lumped together" requirement). Added a `source domain.DirectTaskSource` parameter (threaded through `ChatTaskIntent.Source`) and changed the return signature to also return the created `*domain.DirectTask` (nil unless a dispatch actually happened on this call) so callers can create board items exactly when a real task was created. `http/server.go`'s existing chat call site updated to pass `domain.DirectTaskSourceChat` and discard the new task return value (chat's board-item behaviour is unchanged/out of scope).
7. **Recurring/future Buzz-dispatched tasks do not get a live Buzz-channel reply for each future execution.** `Monitor.pending` only tracks in-flight *immediate* dispatches (so `HandleResult` can publish a reply); a task scheduled for tomorrow, or a recurring task's Nth future run, is executed later by `SchedulerService` outside of any single `Monitor.dispatch()` call, so there is no pending-map entry to match its eventual `TaskResultPayload` against. This mirrors chat's own behavior (the confirmation ack is the only *immediate* feedback; future results only ever land in the Tasks UI/DirectTaskStore, not push back into the original UI surface in real time). Explicitly scoped out — not required by FR-007/FR-008's stated acceptance criteria (Tasks UI visibility + cancel/update reflected in Tasks UI), only flagged here so it isn't mistaken for an oversight.

## Edge Cases & Solutions

- **Duplicate bot-name registration** — handled at the `TeamManager.Run()` Buzz-builder loop level via `Router.Lookup`: if a persona's `buzz.bot_name` already has a registered queue (either from `Run()`'s own team-entry pre-registration, from Slack, or from an earlier duplicate persona in the same loop), that specific persona's Buzz monitor is skipped with a logged error — no `panic`, no effect on other personas or the orchestrator.
- **Incomplete per-persona Buzz config** — unchanged: `buildBuzzMonitor`'s existing early-return-on-missing-field / `LoadKeypair` failure behavior already isolates this per persona; the loop in `Run()` simply calls it once per persona and only calls `WithChannelMonitor` when it returns non-nil.
- **Relay reconnect / message replay dedup** — `BuzzTaskBridge` keeps an in-memory, per-persona, TTL-bounded (`10m`, matching `ChatTaskManager`'s existing pending-intent TTL) set of seen Nostr event IDs; a replayed event ID short-circuits to `BuzzDispatchResult{Duplicate: true}` with no store writes.
- **Schedule cancel racing with in-flight execution** — not redesigned; reuses `ChatTaskManager`'s existing confirm/cancel flow and `LocalTaskDispatcher`'s existing `RunNow`/status semantics verbatim, per spec.md's explicit "reuse, don't redesign" instruction.
- **Malformed/empty schedule text** — `ParseScheduleNL` already falls back to `domain.ScheduleModeASAP` for unparseable text (existing behavior, confirmed by reading `chat_task_manager.go`); the bridge's plain-dispatch branch handles the case where `detectIntent` doesn't even classify the message as a scheduling request at all (fewer than 2 of 3 keyword-group hits) — falls straight through to immediate `DispatchWithSchedule` with `ScheduleModeASAP`.

## Deviations from Plan

See numbered items 1-7 under Technical Decisions above — each is a deviation from architecture.md's necessarily-approximate sketch, made because architecture.md's "Sequence Diagrams" section was explicitly left `[TBD — add during Step 3]` pending this exact tracing work. Summary:

- `domain.TaskPayload` gained a `Source` field (not mentioned in data-dictionary.md) — required to make `execute_task.go:100`'s check reachable at all for both chat and Buzz.
- `Router.Lookup` added to `internal/infrastructure/local/queue` (not mentioned in spec.md's Scope of Changes) — required to avoid a real (pre-existing, now-exposed) `panic` on startup.
- Buzz monitor construction moved into `TeamManager.Run()` via a new `WithBuzzMonitorBuilder` hook, rather than staying a pure loop inside `main.go`'s `run()` as architecture.md's Component Architecture bullet implies — required because the `Dispatcher`/`BoardStore` the bridge needs don't exist until `TeamManager.Run()` creates them.
- `ChatTaskManager.DetectAndHandle`'s signature extended (`source` param, `*domain.DirectTask` return) — required so Buzz-confirmed scheduled tasks are correctly tagged `DirectTaskSourceBuzz` instead of inheriting the hardcoded `DirectTaskSourceChat`.
- `team_manager.go`'s central task-result-handler board-update gate (`task.Source == domain.DirectTaskSourceBoard`) widened to also match `domain.DirectTaskSourceBuzz`, so a Buzz-originated board item's status/`LastResult` actually gets updated on task completion (FR-005's "updates as the task progresses ... reflects completion").
- **`internal/infrastructure/buzz/monitor.go` deviation from spec.md's "Scope of Changes" claim.** *(Added 2026-08-14 per the independent code review's FR-108 item 3 finding.)* spec.md's Scope of Changes section states "No files need to change in `internal/infrastructure/buzz/`... its constructor already supports being called multiple times with distinct identities." In practice `monitor.go` received a substantial change: `git diff 904a732 --stat -- internal/infrastructure/buzz/monitor.go` shows +108/-17 across one file. The change is architecturally sound and was necessary, not a scope-creep mistake: `dispatch()` was split into `dispatchDirect` (the pre-existing direct `queue.Send`/`Worker.Execute` path, preserved as a fallback) and a new `dispatchViaBridge` (routes through the new `domain.BuzzTaskDispatcher` bridge when `WithTaskDispatcher` is set), plus a `publishReply` helper extracted so `HandleResult` and `dispatchViaBridge` share identical reply-event tagging instead of duplicating it. This deviation exists because P2.2 (the Buzz→`Dispatcher`/`DirectTaskStore`/`BoardStore` bridge, FR-005) requires `Monitor.dispatch()` to actually call into the new bridge somewhere — the original "no files change in this package" claim was written before that design detail was worked out at the code level (architecture.md's Sequence Diagrams section was explicitly left `[TBD]` at spec-writing time, same root cause as the four deviations already listed above).

## P1.1/P1.2/P2.3/P3.x — additional findings

8. **P3.2's "update or cancel a previously-created task" scoped to exactly what the existing chat path already supports.** Investigated `internal/infrastructure/http/server.go` for any chat-text-driven mechanism to cancel or in-place-update an *already-confirmed/stored* `DirectTask` (as opposed to a not-yet-confirmed pending intent). None exists: `DELETE /api/v1/tasks/{id}` and the title-rename `PATCH` are REST/operator-UI-only actions, never routed through `ChatTaskManager`. `ChatTaskManager.DetectAndHandle`'s own cancellation branch only ever clears a *pending* (pre-confirmation) intent — the same two-step flow `BuzzTaskBridge` already reuses verbatim. **Decision:** Buzz's "update/cancel" capability is exactly as strong as chat's today — re-issuing an instruction creates a new `DirectTask` (there is no in-place mutation in either channel), and cancellation only applies pre-confirmation. Building a new chat/Buzz-driven cancel-an-already-dispatched-task mechanism would be scope creep against spec.md's explicit "reuse, don't redesign" instruction for this edge case, since no such mechanism exists to reuse. P3.1/P3.2 are satisfied entirely by `BuzzTaskBridge`'s existing `ChatTaskManager` reuse (P2.2) — no additional code required.
9. **`internal/application/team` package's own Buzz-monitor construction loop needed a non-panicking name-collision guard beyond `queue.Router.Lookup`.** `buildBuzzMonitor`'s per-call `Lookup`-before-`Register` alone is not sufficient for the "two personas' own `config.yaml` both set the same `buzz.bot_name`" edge case: it would make the second persona's monitor silently reuse the first's queue (found via `Lookup`) instead of failing loudly. Added a `buzzBotNamesUsed` set inside `TeamManager.Run()`'s Buzz-builder loop, checked *before* invoking `BuzzMonitorBuilder`, so a duplicate `buzz.bot_name` is caught and logged at the loop level (that persona's monitor is skipped entirely) rather than silently sharing a queue between two distinct Buzz identities. Regression tests: `TestTeamManager_BuzzMonitorBuilder_DuplicateBotName_IsolatedNotPanic` and the two other `TestTeamManager_BuzzMonitorBuilder_*` tests in `team_manager_test.go`.
10. **Pre-existing `go test -race` failure in `internal/infrastructure/buzz`, confirmed unrelated to this feature.** `go test -race ./internal/infrastructure/buzz/...` fatally crashes (`fatal error: checkptr: pointer arithmetic result points to invalid allocation`) inside the vendored `fiatjaf.com/nostr` dependency's `writeJSONString` (`event.go:245`), triggered by any test that exercises the real `RelayClient`'s JSON event serialization (e.g. `TestE3_NIPOAAuthTagIncludedOnAuthEvent`, `TestConnect_PublishesProfileOnFirstConnect`) under Go 1.26.0's race-detector `checkptr` instrumentation. **Confirmed pre-existing**: reproduced identically on base commit `262aba0` (before any of this feature's changes), in an isolated `git worktree`. This is a fatal, whole-test-binary-crashing failure, not a benign data race — it is a third-party-library/Go-toolchain-version incompatibility, entirely out of this feature's scope to fix. `go test ./internal/infrastructure/buzz/...` (without `-race`) is fully green, including every new bridge test this feature adds. Every other package in the module, including all of this feature's own new/modified code, is fully `-race`-clean.
11. **P2.3's "-race test with concurrent simulated dispatch from 2+ monitors" implemented at the `internal/application/orchestrator` layer, not `internal/infrastructure/buzz`.** *(Corrected 2026-08-14 per the independent code review's FR-105 finding — see `specs/260814-boabot-native-daemon-mode-auto-review/`.)* `.github/workflows/boabot.yml`'s CI `Test` step already invokes `go test -race -gcflags=all=-d=checkptr=0 ./...` — a workaround predating this feature by a full spec cycle (`specs/260804-boabot-buzz-support`) — and with that flag, `-race` on the whole module including `internal/infrastructure/buzz` is fully green (verified directly: zero failures, 72 packages). So finding #10's crash is **not** a reason a concurrency test placed inside `internal/infrastructure/buzz` "would be unable to run under `-race` at all" — that claim was wrong. The real reason `TestBuzzTaskBridge_ConcurrentMultiPersonaDispatch_NoCrossTalk` (`buzz_task_bridge_concurrency_test.go`) lives at the `internal/application/orchestrator` layer instead is architectural: simulating "N monitors" as N goroutines calling `BuzzTaskBridge.Dispatch` directly isolates the `DirectTaskStore`/`BoardStore`/`Router` concurrency guarantee this test exists to lock in (architecture.md's decision) from relay-layer noise — real network I/O, JSON (de)serialization, NIP-42/NIP-OA auth handshakes — that a `internal/infrastructure/buzz`-level test would otherwise have to set up and that has nothing to do with the guarantee being tested. Either placement is buildable and race-clean under CI's actual invocation; this file's own package (`internal/application/orchestrator`) was chosen for narrower, faster, more focused test setup, not because the other layer is untestable.

## Post-implementation review findings (advisor pass)

12. **Buzz-sourced task completions were leaking the raw Nostr channel UUID into the shared operator chat feed as a message `ThreadID`.** `team_manager.go`'s shared `TaskResultHandler` closure ("Register result handler on every bot so any bot's reply surfaces in chat") appends an inbound `ChatMessage` for *every* tracked (`sharedTasks`-resident) task's completion, regardless of source — this is pre-existing, deliberate behavior, not something this feature added (board- and operator-sourced tasks already surface there today, with an empty `ThreadID` since both dispatch with `threadID=""`). Before this feature, Buzz tasks were never in `sharedTaskStore` at all (P1.0's direct-`queue.Send` bypass), so this code path never ran for them. Post-bridge, they are tracked, so the same code now runs for Buzz too — but `msg.ThreadID = task.ThreadID` would have set it to the *Buzz channel UUID* (needed by `BuzzTaskBridge`/`ChatTaskManager`'s own scheduling-confirmation pending map), not `""` like board/operator. That UUID doesn't correspond to any registered `domain.ChatThread`, and `GET /api/v1/chat`'s flat listing (`handleChatList`) only excludes `board-`-prefixed `ThreadID`s — so it would have rendered as an orphaned, mislabeled thread grouping in the operator's chat feed, which is not what spec.md's non-goal ("this only makes [Board/Tasks] populate from Buzz-triggered work") intends. **Fix:** added `chatMessageThreadID(task domain.DirectTask) string`, returning `task.ThreadID` only for `DirectTaskSourceChat` and `""` for every other source (board/operator/buzz) — makes the pre-existing "every completion surfaces in chat" behavior consistent across all non-chat sources instead of singling out Buzz for suppression (which would have been an inconsistent, undocumented special case relative to how board/operator are already treated). Regression test: `TestChatMessageThreadID`.
13. **Verified safe: `techLeadPool.Deallocate` fires (harmlessly) for Buzz-created board items that were never `Allocate`d.** `InMemoryBoardStore.Update`'s `statusChangeHook` fires `techLeadPool.Deallocate(ctx, item.ID)` on any `InProgress → *` transition, including a Buzz-originated board item's completion (created directly as `InProgress`, never routed through `techLeadPool.Allocate`, unlike a board-dispatched item). Read `pool.Deallocate` (`internal/application/pool/pool.go:146-159`): an unknown `itemID` returns a plain `fmt.Errorf("pool: no entry found for itemID %q", itemID)` *before* any mutation of `p.entries` (the not-found check is the first thing after acquiring the lock) — no state is touched. The call site (`team_manager.go`) already only `slog.Warn`s on this error. Confirmed harmless; no code change needed.

## Lessons Learned

- `architecture.md`'s "Sequence Diagrams: [TBD — add during Step 3 ... a diagram before that would misrepresent the current-state side]" was the right call — the actual current-state wiring (queue-direct dispatch, `Message.From`-as-`Task.Source`, `Run()`-time shared-store creation) had enough non-obvious structure that a diagram sketched from spec.md alone would have missed the `TaskPayload.Source` gap and the `Run()`-timing constraint entirely.
