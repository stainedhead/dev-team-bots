# Implementation Notes: Buzz DM Support and Full Threaded-Reply Support

**Created:** 2026-08-14

Record technical decisions, edge cases, deviations from the plan, and lessons learned as implementation proceeds. Update this file continuously during Phase 5 — do not leave it until the end.

## Technical Decisions

- **`KnownThread` keying**: `botName + "|" + threadID`, sibling `dispatchedThreads map[string]time.Time` on `BuzzTaskBridge`, no TTL/eviction (unlike `seenEvts`) — matches architecture.md's RQ1 resolution that conversation relevance fades via the 10-message `ChatStore` replay window rather than a separate dormancy mechanism.
- **`triggerThreadReply` root resolution**: a new `threadReplyCandidates(evt)` helper (trigger.go) collects root-marked, reply-marked, *and* positional (first/last, deprecated NIP-10 convention) `e`-tag values, deduplicated, and tries each against `KnownThread` in that priority order. `rootEventID` alone (root-marked tag only, else `evt.ID`) would miss a real in-thread reply that only carries a `reply`-marked tag or uses the older positional convention — exactly the case P1.2 exists to fix.
- **`dispatch()`'s root is now caller-supplied**, not internally recomputed: `handleChannelEvent` computes `root` once (via `rootEventID` for a mention, or the matched `KnownThread` candidate for a thread-reply) and threads it through `dispatch`/`dispatchDirect`/`dispatchViaBridge`/`awaitResult`/`publishReply` — this is what makes `ThreadID` consistent between the value checked against `KnownThread` and the value actually used for dispatch/continuation.
- **NIP-10 outbound completion (P1.4)**: `publishReply` gained `parentEventID`/`authorPubKey` parameters, carried end-to-end via an extended `replyTarget` struct (`pendingEntry`). The reply-marked `e` tag is omitted when `parentEventID == root` (replying directly to the thread root needs only the one root-marked tag per NIP-10 — a duplicate reply tag pointing at the same ID adds nothing).
- **ChatStore ownership (P1.5)**: both the inbound-message append and the "prior conversation" history-replay read live in `BuzzTaskBridge.Dispatch` (application layer, matches architecture.md's stated ownership). The **outbound** (bot-authored reply) append is owned by `Monitor.recordOutbound`, called from both `publishReply` (channel) and `publishDMReply` (DM) — deliberately *not* routed through the existing generic `team_manager.go` `WithTaskResultHandler`/`chatMessageThreadID` mechanism, because `chatMessageThreadID` explicitly returns `""` for non-chat sources today (to keep Buzz threads out of the `GET /api/v1/chat` global feed's `board-`-prefix-style exclusion convention) — routing outbound Buzz replies through it would have required either breaking that invariant or adding a parallel one. Keeping both directions inside the Buzz-specific code path is self-contained and doesn't touch the general chat plumbing at all.
- **10-message replay window, most-recent not oldest**: `BuzzTaskBridge.buildInstructionWithHistory` intentionally does **not** byte-for-byte mirror `handleChatSend`'s own windowing loop. See Deviations below.
- **DM `threadID` shape**: `"dm:" + counterparty-pubkey-hex` (`dmThreadID`), distinguishable at a glance from a bare 64-hex channel thread root in logs/UI.
- **DM origin labeling**: a `"[Buzz DM] "` prefix (`dmBoardLabel`) is prepended to the dispatched instruction text for DM-originated tasks only. Since board-item title/description are derived directly from the instruction string (`buzzBoardTitle`), this satisfies "visibly labeled DM-originated" (FR-203) via the existing title/metadata convention (per data-dictionary.md's explicit "no new `DirectTaskSource` value" decision) with zero signature changes to `Dispatch`/`BuzzTaskDispatcher`.
- **`nostr.Keyer` adapter reuses the vendored library's own implementation**: `NewDMKeyer` is a thin wrapper around `fiatjaf.com/nostr/keyer.NewPlainKeySigner` — no hand-rolled NIP-44 encrypt/decrypt or Schnorr signing. `nostr.SecretKey` is `[32]byte` (an unnamed underlying type), so it's directly assignable to `NewPlainKeySigner`'s `[32]byte` parameter without conversion.
- **DM support activates unconditionally whenever channel Buzz activates** (no separate `buzz.dm_enabled` config field): `buildBuzzMonitor` always wires `WithDMKeyer(buzzinfra.NewDMKeyer(sk))` once `sk` is resolved, matching spec.md's Goal "any Buzz-enabled persona with a provisioned key is reachable via a direct 1:1 message ... no separate DM key."
- **`domain.RelayClient`/`relayClient` interfaces gained `PublishRaw(ctx, Event) error`**, a sibling to `Publish` that does *not* sign the event or overwrite its `PubKey`. This is load-bearing, not cosmetic: `RelayClient.Publish` always does `nevt.PubKey = rc.pk; nevt.Sign(rc.sk)`, but `nip59.GiftWrap`'s outer envelope is *always* signed with a freshly-generated ephemeral key (`nostr.Generate()`), never the caller's real key — routing a gift-wrapped event through `Publish` would silently defeat NIP-17's sender-anonymity property *and* break the recipient's ability to decrypt at all (`GiftUnwrap` derives the seal's conversation key from the envelope's own `PubKey` field). `PublishRaw` forwards the already-signed event verbatim via the existing `relayConn.Publish(ctx, nostr.Event)` seam, which itself never signs.

## Edge Cases & Solutions

- **Self-message loop (spec.md's flagged risk)**: `handleDMEvent` checks `rumor.PubKey == selfPK` (resolved via `dmKeyer.GetPublicKey`) *before* the author gate and *before* dispatch — `nip17.PrepareMessage`'s `toUs` self-copy is silently skipped, not logged as an error (it's expected, ordinary traffic). Covered by `TestMonitor_HandleDMEvent_SelfCopy_NotDispatched`.
- **Relay-replay of a DM event**: reused the existing `BuzzTaskBridge.checkAndMarkSeen`/`unmarkEvent` dedup exactly as-is — the outer gift-wrap event's own ID (`evt.ID`, pre-unwrap) is passed as `Dispatch`'s `eventID`, same mechanism channel mentions already use. No new dedup code was written for DMs.
- **Malformed/corrupted gift-wrap event**: `nip59.GiftUnwrap` failure (bad ciphertext, wrong recipient, corrupted seal signature, non-JSON payload) is caught, logged (event ID only, see Deviations/log-safety below), and skipped — never crashes `dmLoop`'s goroutine. Same treatment for an untranslatable `domain.Event` (bad hex ID from a non-conformant relay) before gift-unwrap is even attempted.
- **Relay doesn't support kind:1059**: `startDMSubscription`'s `Subscribe` failure is logged and isolated — channel discovery/membership-watch, already started earlier in `run()`, are completely unaffected. Verified by `TestMonitor_StartDMSubscription_SubscribeError_LoggedNotFatal` and the existing per-monitor failure-isolation pattern.
- **Thread reply to a root this persona never dispatched in**: `KnownThread` is keyed `botName + "|" + rootID`, never just `rootID` — verified by `TestBuzzTaskBridge_KnownThread_StrictlyPerPersona`.
- **Concurrent replies in the same thread / concurrent DM conversations**: covered by the existing `-race` test suite; `dispatchedThreads` map access is guarded by the same `b.mu` lock as `seenEvts`.

## Deviations from Plan

1. **DM subscribe/publish uses the existing single-relay `relayClient` seam, not `nip17.ListenForMessages`/`PublishMessage` directly.** Both of those library functions require a `*nostr.Pool`, which this codebase does not have and was never going to introduce — `Monitor` is built entirely around a single-relay abstraction (FR-201 explicitly requires "using the same relay connection ... it already uses for channel participation"). Introducing a parallel `nostr.Pool`-based connection just for DMs would have violated that requirement and duplicated connection-management logic `RelayClient` already owns. Concretely:
   - **Outbound** still uses `nip17.PrepareMessage` directly — it only needs a `nostr.Keyer`, no `Pool` — and its two gift-wrapped outputs are published via the new `relayClient.PublishRaw`, not `nip17.PublishMessage` (the Pool-based convenience wrapper).
   - **Inbound** uses the existing `relayClient.Subscribe` (kind:1059, `#p`-tagged to self — the exact filter guard.go's p-gate already requires) plus `nip59.GiftUnwrap` called directly — the identical primitive `nip17.ListenForMessages` itself calls internally, just without the `Pool`-owning wrapper around it.

   This is the smallest deviation that both satisfies architecture.md's "use `nip17`'s high-level API, not raw `nip44`/`nip59` calls" (still true for outbound, and for inbound the only "raw" call is `nip59.GiftUnwrap`, the same call `nip17` itself makes) and preserves NIP-17's privacy properties exactly (both code paths still go through `nip59.GiftWrap`/`GiftUnwrap`, never through `nip44` directly). Documented here per the "make the most reasonable call, document as deviation" instruction — this was not resolvable from spec.md/architecture.md/research.md alone, since none of them anticipated the `*nostr.Pool` requirement.

2. **`buildInstructionWithHistory`'s replay window is the 10 most-recent prior messages, not a byte-for-byte mirror of `handleChatSend`'s own windowing loop.** `handleChatSend`'s loop (`for i := len(history)-1; i >= 1 && len(prior) < 10; i--`) walks from the *oldest* message toward the newest and stops after collecting 10 — which selects the 10 **oldest** prior messages once a thread exceeds 11 total messages, not the 10 most recent. This was caught by `TestBuzzTaskBridge_Dispatch_ChatStore_CapsAtTenPriorMessages` (initially red against a literal mirror). Buzz threads/DMs are expected to run materially longer than typical web-UI chat sessions, so this latent behavior would have been reached routinely, not as a rare edge case. Fixed to explicitly window to the 10 most-recent prior messages (still assembled oldest-first for the replayed block) — matching every FR/spec.md description of the intended behavior ("last 10 messages," "recent ChatStore history"). Not fixing `handleChatSend` itself — out of scope for this feature, and changing shared HTTP-handler behavior wasn't requested.

3. **Unauthorized-DM handling (FR-204) defaults to silent ignore, not a decline reply** — per the task brief's explicit instruction, this is the more conservative choice (a decline reply to an unauthorized sender could leak which personas exist/respond to an arbitrary Nostr identity, a materially larger exposure surface than curated channel membership). Flagged here for the operator to override later if the alternative (an explicit decline reply) is preferred; no code currently implements a decline-reply path.

4. **Two additional non-decrypt error logs (`dm gift-unwrap failed`, `prepare dm reply failed`) were changed to omit the underlying library error's text**, discovered during the P3.1 audit: `nip44.GenerateConversationKey` (called transitively by `dmKeyer.Encrypt`/`Decrypt` for every DM operation) has an error path — an out-of-range secret key — that formats the **raw secret-key bytes** into its error string (`fmt.Errorf("invalid private key: x coordinate %x is not on the secp256k1 curve", sk[:])`, vendored `nip44/nip44.go:170`). `LoadKeypair`'s own validation (reject all-zero, require valid pubkey derivation) makes this unreachable for a persona's own key in practice, but the only way to satisfy the "no private key ... appears in any log statement" requirement *unconditionally* (not merely "in practice, today") is to never let that specific error's text reach a log call at all. Every other failure on those two call sites (invalid ciphertext shape/base64/HMAC/padding, bad signature, non-JSON payload) is adequately described by the event ID alone. Verified by `TestMonitor_HandleDMEvent_MalformedDM_NoErrTextLogged` and the two plaintext/key-leak log-capture tests.

5. **A Buzz-dispatched task's outbound reply is now recorded twice in `tm.sharedChatStore`, and Buzz conversations now surface in the operator's `GET /api/v1/chat` global feed** — an accepted, deliberate tradeoff, not an oversight. `team_manager.go`'s existing `WithTaskResultHandler` (registered on every bot) already appends every task's output to `sharedChatStore` once `sharedTasks.Get` finds the task tracked — which it does for Buzz-dispatched tasks too, since `BuzzTaskBridge`'s `dispatcher` is the same `LocalTaskDispatcher` backed by `tm.sharedTaskStore`. That existing append uses `chatMessageThreadID(task)`, which returns `""` for `DirectTaskSourceBuzz` (by design, predating this feature, specifically to keep Buzz activity out of the global chat feed). P1.5/P2.4's new `Monitor.recordOutbound` appends the *same* reply a second time, this time correctly `ThreadID`-keyed (`root` or `dm:<pk>`), because that correct keying is what `BuzzTaskBridge.buildInstructionWithHistory`'s `ChatStore.List(threadID)` needs to find it on the next turn.

   Changing `chatMessageThreadID` to pass Buzz `ThreadID`s through (removing the duplicate) was considered and rejected for this pass: `recordOutbound` only fires *after a successful publish*, so relying on it alone would mean a relay-publish failure leaves **no** chat record of the bot's output at all — a real regression from today's behavior, where the `""`-keyed copy is written by the generic result handler regardless of Buzz's own publish outcome. Fixing this properly needs the generic handler to stop writing the `""` copy for Buzz sources while `recordOutbound` (or an equivalent hook the generic handler itself calls) becomes the single source of truth for *both* success and failure cases — a small but real design change to shared, non-Buzz-owned code (`team_manager.go`), which is more than this pass's scope should touch without an explicit go-ahead.

   **Net effect, accepted as-is:** inbound Buzz/DM messages and bot replies now appear in the operator's global chat screen (previously excluded), and every reply appears as two rows (one `ThreadID=""`, one correctly keyed). FR-206 (conversation continuation) is unaffected — `ChatStore.List(ctx, threadID)` filters by threadID, so the `""`-keyed duplicate is simply invisible to the replay logic. Flagged here for the operator/reviewer to decide whether the UI noise and duplication are acceptable or warrant the follow-up fix described above.

6. **FR-207's literal wording ("channel and DM") is read against the Success Criteria's actual acceptance test, not the FR text alone.** Outbound DM replies (`publishDMReply`, via `nip17.PrepareMessage`) carry only the recipient's `p` tag `PrepareMessage` itself adds -- no root/reply `e` tags, since NIP-17 1:1 DM conversations aren't NIP-10-threaded (there is no "channel" for an `e`/`h` tag to reference). spec.md's Success Criteria list separate, distinct acceptance lines for channel replies ("carry root `e`, reply `e`, and `p` tags") versus DM replies ("correctly gift-wrapped and decrypt correctly for the sender") -- only the channel line names the three NIP-10 tags. Implemented to match the Success Criteria's actual per-channel/per-DM split, not FR-207's broader summary sentence. Flagged here in case a reviewer expects FR-207's literal text to require NIP-10 `e` tags on DM replies too.

7. **`!shutdown` is reachable via a channel mention but not via DM** — `handleDMEvent` never routes to `handleShutdownCommand`. This mirrors FR-204's conservative default (DMs are reachable from any Nostr identity, unlike curated channel membership) rather than an oversight: extending the wider FR-026 shutdown gate to an unauthenticated-by-relay-membership DM surface was not requested by any FR and would meaningfully widen the shutdown attack surface for no stated requirement. If DM-triggered shutdown is wanted later, it is a small, isolated addition (call `handleShutdownCommand`-equivalent logic from `handleDMEvent` before the author-gate check, using the same `allowsShutdown` three-way gate).

## Lessons Learned

- Writing the FR-208 regression test (`TestMonitor_Dispatch_ConcurrentThreadsSameChannel_IndependentThreadIDs`) immediately surfaced that one pre-existing test (`TestMonitor_Dispatch_WithTaskDispatcher_UsesBridgeNotQueue`) was itself asserting the pre-fix buggy behavior (`ThreadID == channelUUID`) as its expected value — a useful reminder that a fix's own regression coverage should include auditing existing assertions for ones that encode the bug being fixed, not just adding new tests.
- The `nip17`/`nip59` Pool requirement (Deviation 1) was not visible from spec.md/architecture.md/research.md — all three assumed `nip17.ListenForMessages`/`PublishMessage` could be called directly. Reading the vendored library's actual source before writing any wiring code (rather than trusting the research doc's function-signature summary) caught this before any code was written against the wrong assumption.
