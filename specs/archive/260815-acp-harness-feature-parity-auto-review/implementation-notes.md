# Implementation Notes: ACP Harness Feature Parity — Code Review Fixes

**Created:** 2026-08-15

Record technical decisions, edge cases, deviations from the plan, and lessons learned as implementation proceeds. Update this file continuously during Phase 5 — do not leave it until the end.

## Technical Decisions

### T-FR1 (P0) — board.json cross-process concurrency fix

- **New package `internal/infrastructure/local/filelock`** (not a refactor of `internal/infrastructure/buzz/lock.go`, per architecture.md's explicit "not modified itself" integration note). It reimplements the same atomic-publish (same-directory temp file + `os.Link`) and PID-liveness stale-lock-reclaim mechanics as `lock.go`, but exposes `AcquireWait(path, timeout)` — a wait-your-turn, retry-with-backoff acquire (capped exponential backoff, 2ms→50ms) — instead of `lock.go`'s fail-fast `AcquireLock`. Kept independent of `buzz` deliberately, to avoid an awkward cross-adapter dependency (`orchestrator` importing `buzz`) for a small amount of shared logic, and to avoid risking `buzz/lock.go`'s existing, carefully-verified FR-031/FR-004 test coverage and Windows-portability doc trail by refactoring it.
- **`board.go`'s `persist()` signature changed** from `persist()` (serializes the *entire* in-memory `s.items`) to `persist(upsert []domain.WorkItem, deleteIDs []string)` (writes only this call's own touched item(s)/deletion(s), merged with a fresh read of on-disk state). This is a deliberate deviation from architecture.md's literal wording ("re-read disk into a fresh map, merge with in-memory state") — passing the *specific* touched item(s)/deleted ID(s) rather than the *entire* `s.items` map is sufficient and safer: because every mutation already calls `persist()` immediately (the existing invariant), on-disk state is always a superset of everything this process has ever persisted, so re-merging the *whole* in-memory map on every call would be redundant work, not additional correctness. Recorded here since it's a design choice beyond what architecture.md spelled out, not a correction of it.
- **Lock timeout (5s) failure mode:** if `filelock.AcquireWait` times out (e.g. a genuinely wedged holder), `persist()` silently skips the write rather than falling back to the pre-fix full-in-memory-overwrite — falling back would reintroduce the exact clobbering hazard this fix exists to close. This matches the existing "best-effort, silent-skip on failure" style already present throughout `persist()` (marshal errors, `MkdirAll` errors, etc. were already silent no-ops pre-fix).
- **`Reorder`'s accepted limitation** is now stated directly in `Reorder`'s doc comment in `board.go` (not just in this file and architecture.md): two processes reordering the *same column* concurrently can still produce colliding/gapped `SortPosition` values under the per-item merge. Only file-level clobbering of *other* items is solved.

## Edge Cases & Solutions

- **Lock-timeout write loss is no longer self-healing.** Pre-fix, `persist()` serialized the *entire* in-memory `s.items` on every call, so a transient write failure self-healed on the very next mutation (any later `persist()` re-wrote everything, including whatever the failed call was trying to write). Post-fix, `persist()` writes only its own targeted `upsert`/`deleteIDs` args, so if `filelock.AcquireWait` times out (`persistLockTimeout`, 5s — only reached if a lock holder is genuinely wedged), that specific item's write is dropped and is **not** automatically retried: it reaches disk only if that same item is mutated again later. Narrow window (5s is generous relative to a sub-millisecond marshal+write), judged not worth a dirty-set/retry-queue for this fix's scope, but recorded here as a genuine (if narrow) behavior change introduced by the targeted-upsert deviation below, not a pre-existing gap.
- **`Create`'s `SortPosition` computation is still per-process-local** (`sameStatus` is counted from this process's own in-memory `s.items`, not a disk re-read). Two processes concurrently creating items in the same column can still compute the same `SortPosition` for both. Out of scope for T-FR1 (same class of accepted limitation as `Reorder`'s same-column race, not the file-clobbering hazard this fix targets) — not fixed here.
- **`Update`'s existence check (`ErrWorkItemNotFound`) is against in-memory state, not disk.** A process that has never `Get`/`List`'d an item created purely by another process will return `ErrWorkItemNotFound` for `Update(thatItem)` even though it exists on disk. This is the same accepted per-process read-staleness architecture.md already scopes out ("Read-only calls continue reading from in-memory state ... acceptable staleness window for reads") — noted here because `Update`'s existence check is technically a read path that surfaces as a write-path error, which is easy to miss.
- **Delete vs. concurrent Create/Update from another process on the same ID is not specially handled** — the merge is a straightforward "apply my upsert/delete on top of a fresh disk read," so if process A deletes item X in the same window process B is updating item X, whichever call's `persist()` runs later wins for that one ID. This is exactly the "own touched item(s) win" semantics the spec calls for; full concurrent-edit-of-the-same-item resolution was explicitly out of scope.

## Deviations from Plan

- `persist()`'s signature (see Technical Decisions above) takes targeted upsert/delete arguments instead of the full in-memory item set, a refinement of architecture.md's "re-read disk, merge by item ID" description rather than a contradiction of it. No other deviation from the resolved research.md/architecture.md design.
- Added a second, hook-based regression test (`board_race_test.go`, package `orchestrator`, white-box) beyond the plan's single cross-process test, to explicitly force the lock-contention/retry-backoff window via a test-only hook (`persistAfterLockHook`), directly mirroring `lock_race_test.go`'s technique per the task's explicit instruction. The first, simpler test (`board_concurrency_test.go`, package `orchestrator_test`, black-box, no hook) was written and verified failing FIRST (TDD red step, 100% deterministic failure against the unfixed `persist()` — confirmed over 5 repeated runs, always exactly 1 of the 2 items survived) since it required no production-code changes to compile or run; the hook-based test was added alongside the fix itself, since the hook it needs (`persistAfterLockHook`) only exists once the lock-acquisition code path it hooks into exists.

### T-FR5 (P2, optional) — decision: defer, not implemented

Per spec.md's own acceptance criterion ("decision recorded ... not required to close"), the gating-logic duplication across `team_manager.go`'s `startBot` and `acp.go`'s `buildACPMCPOptions`/`buildACPWorker` is **not** being extracted into shared functions in this pass. Reasoning:

- The review PRD itself frames this as matching existing precedent (`cmd/boabot/main.go`'s `buildBuzzMonitor`/`newBuzzMonitorBuilder` already duplicates native-mode wiring shape in the `cmd` layer) — not a new anti-pattern this branch introduces, and explicitly "no fix required to merge."
- T-FR2/T-FR3's fixes just added detailed, precise comments at each of the three gate sites in `acp.go` explaining exactly how each one relates to `team_manager.go`'s corresponding condition (same field vs. different field vs. same field/different scope) — extracting these into shared functions now, immediately after writing those comments, would either discard that just-written context or require re-deriving it inside the new shared functions, with no functional benefit in the same change.
- The extraction itself is not "trivially small": it would need `internal/application` (both `cmd` and `internal/application/team` already depend on it, satisfying Clean Architecture's dependency direction) to gain three new small pure functions, threading `entry.Type`/`cfg.Bot.BotType`, `Orchestrator.Plugins.InstallDir`, and `Orchestrator.CLITools` through a new shared signature on both call sides, each with its own test coverage — a real, if small, unit of work better done as its own reviewed change than folded into a P0-plus-docs fix pass.

## Lessons Learned

- The pre-fix bug was even more deterministic than "a race" implies: because neither `InMemoryBoardStore` instance in the regression scenario ever observes the other's item (each loads `persistPath` exactly once, at construction, before either has written anything), the pre-fix clobber isn't scheduler-timing-dependent at all — whichever `persist()` call is *last* to complete always wins with only its own single item, 100% of the time. This made the RED step unusually clean to verify (no flakiness to rule out) but also underscores why the bug was such a clear P0 in production: it's not a rare interleaving, it's the *guaranteed* outcome of two long-lived processes each doing "full in-memory overwrite, no re-read."
