# Implementation Notes: ACP/Native Shared State and Task-Layer Parity

**Created:** 2026-08-16

## Purpose

Running log of technical decisions, edge cases, and deviations discovered during implementation. Update as Step 3/9 progress — this is the durable record `write-flow-analys` and future readers rely on.

## Technical Decisions

- **FR-501 redesigned during implementation.** A verification pass (before writing any FR-501 code) confirmed the PRD's original wording — "fail loudly if native mode's config and an ACP persona's config diverge" — cannot be implemented: an ACP worker process only ever loads its own persona `config.yaml` (`resolveACPConfigPath` in `acp.go`), never native mode's separate top-level config, and native mode may not even be running at the time. There is no cross-process channel to compare against. Implemented instead: a marker file (`sharedstate.EnsureOwner`, new package `internal/infrastructure/local/sharedstate`) inside the shared directory itself, recording the identity that claimed it. This catches identity drift/collision within an already-shared directory (checkable with no cross-process communication) but does NOT catch two processes configured to point at genuinely different roots when they were meant to share — that case is undetectable by construction and is called out explicitly rather than silently claimed as solved. `spec.md`'s FR-501 and AC1 were updated to match.
- **No new config field for the shared-state root.** `memory.path` already exists on both native mode's top-level config and every ACP persona's config, and both already resolve board/chat/task paths from it (native: `MemoryRoot` + orchestrator name; ACP: `cfg.Memory.Path` + `cfg.Bot.Name`, falling back to exe-dir if empty). Adding a second, redundant field (`shared_state.root`) would duplicate this without adding capability — the "make it explicit" goal is served by (a) documenting that operators should set `memory.path` explicitly on any ACP persona meant to share state with native mode, and (b) the marker file catching the failure mode that actually matters (accidental collision/drift), not by inventing a parallel config surface.
- **Pre-existing bug found and fixed as a dependency of this feature, not a new feature.** `ChatStore` and `DirectTaskStore` already existed (used by native mode) but their `persist()` methods had the same unlocked-write clobber bug `board.json` had before its P0 fix — undetected until now because neither store was genuinely shared cross-process before this feature. Fixed by applying the identical `filelock`-based re-read-merge-write pattern `board.go` already established. Regression tests confirmed genuinely red (deterministic across 20 runs) before the fix.
- **Pre-existing race fixed as a dependency of this feature.** `TeamManager.cancel` was written in `Run()` and read-then-called in `Shutdown()` with no synchronization — a real data race, confirmed pre-existing by reverting this feature's `sharedstate.EnsureOwner` call and reproducing the same race under repeated `-race` runs against the unmodified code. This feature's `EnsureOwner` call (a real filesystem fsync) widened the scheduling gap between goroutine launch and the `tm.cancel` write enough to make the race reliably reproducible, surfacing a bug that was previously rare. Fixed with a dedicated `cancelMu` mutex (`setCancel`/`callCancel`), verified clean across 8 repeated `-race` runs.
- **`resolveThreadID`'s session-ID fallback provides real DM continuity, not just channel continuity.** `extractChannelID` only finds a channel UUID for channel-scoped turns; a DM-scoped turn has no channel block (per `publisher.go`'s own doc comment), so `resolveThreadID` falls back to the ACP session ID. Verified against a live `buzz-acp` log from this session (`~/Library/Application Support/xyz.block.buzz.app/agents/logs/`) that individual `session_id` values recur across 2–10 log lines each (i.e. multiple `Prompt` calls share one session, not one session per turn) — confirming buzz-acp reuses a session across a conversation rather than minting a fresh one per turn. FR-503/504/504a's continuity and scheduling therefore work for DM-scoped conversations too, not only channel-scoped ones.

## Edge Cases & Solutions

- A `ChatTaskManager`-confirmed scheduling intent that resolves to an ASAP schedule (no time/recurrence keyword in the original message, e.g. "create a task for the architect") has no valid target in ACP mode's single-persona process — native mode's `LocalTaskDispatcher` would route it to a different bot's message queue, a multi-bot concept ACP mode doesn't have. Solved with `NoImmediateDispatchQueue` (dispatch.go): `Send` fails immediately and predictably, and `turn.go` catches the resulting error and replies with a clear explanation instead of a raw error string. The `DirectTask` record itself still persists (created by `LocalTaskDispatcher` before delivery is attempted) marked `failed` — honest observability, not a silent drop.
- A scheduled (Future/Recurring) `DirectTask` created via ACP mode's `ChatTaskManager` pre-check only ever *fires* if native mode's `SchedulerService` is running against the same shared `tasks.json` — ACP mode has no scheduler loop of its own (by design, per this feature's Non-Goals). This is a known, accepted limitation: the acceptance criterion is "visible under the Scheduled filter," which is satisfied, but a scheduled task created purely through a standalone ACP deployment (no native mode running against the same shared state) will never execute. Not a bug — an inherent consequence of ACP mode being single-persona/no-scheduler by design — but worth calling out explicitly for anyone deploying ACP mode standalone.

## Deviations from Plan

- FR-501 shipped as a marker-file safety net (`sharedstate.EnsureOwner`) rather than the "explicit shared-state config + fail loudly on divergence" originally specified — see Technical Decisions above for why the original wording was not implementable and what was built instead.

## Lessons Learned

- When adding filesystem I/O (even a single, infrequent lock acquisition) to a hot construction path shared by many parallel unit tests, verify test suite stability under `-race` with repeated runs before treating a subsequent CI failure as flaky infrastructure — the added scheduling delay can turn a rare, pre-existing race into a reliably-reproducing one, which is a genuine service to the codebase (a latent bug found), not a new defect, but easy to misdiagnose as "my change caused a race" instead of "my change surfaced one."
